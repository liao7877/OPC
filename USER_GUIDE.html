OPC 用户手册

你不需要先理解内部目录和编号。日常只做三件事：把需求说清楚、在关键节点拍板、对结果验收。任务拆分、派发、留痕、看板和巡检由总管、员工与机制共同完成。

1 · 一分钟开始

1
首次使用：在 OPC 根运行 bootstrap，完成锚、钩子、索引、看板和本地服务初始化。
2
打开总管：把本公司的总管目录作为工作区开启新会话。总管会加载组织规范和岗位能力。
3
说目标：先讲要得到什么结果。信息不足时，总管会逐个澄清关键问题，再给方案或开始执行。
示例：这周帮我把公众号选题和生产流程梳理成一套能执行的方案，先调研现状，再给我关键决策点和实施计划。

高级目录、编号和维护命令不是日常使用前置条件。需要排障时再查看 README。

2 · 这件事该找谁

默认找总管。跨角色、需要拆单、涉及公共制度或你不确定负责人时，总管是稳定入口。
任务类型建议入口说明
跨角色、正式项目、制度或机制总管负责澄清、拆分、分派、跟踪和汇总验收。
售前、需求分析、方案范围售前工程师适合客户需求、用例、边界和方案建议。
排期、依赖、风险、交付协调项目经理适合项目推进和跨角色协调。
设计、开发、测试、架构对应专业员工目标和责任已明确时可以直派。
内容、课程、动效、剪辑对应内容角色给清资料、渠道、成品形态和验收标准。
提醒、整理和私人事务私人助理适合低耦合、个人化的持续事务。

角色和团队以当前公司的 roster 为准。员工遇到公共领地或权限边界，会转报总管，而不是自行改动。

3 · 怎样把任务说清楚

高质量派活不需要专业模板，但最好包含五项：

目标

最终要改变什么，而不只是“做一个文件”。

背景与资料

为什么做，已有内容在哪里，哪些事实不能猜。

交付物

代码、报告、页面、方案、视频或其他成品形态。

验收标准

你将依据哪些条件判断合格。

时限与优先级

什么时候需要，和其他任务如何取舍。

把项目资料中的客户访谈整理成一页决策建议。交付 HTML，重点回答是否值得立项、最大风险和下一步；引用原始证据，今天 18:00 前给我审。
信息不全时可以直接说“先帮我澄清需求”。不要为了显得完整而编造验收标准或路径。

4 · 选择工作车道

直聊

适合问答、一次性小改、无需独立验收和交接的工作。员工仍按 worklog 纪律记录关键结果，但普通聊天不会被平台自动完整持久化。

正式工单

适合需要验收、跨会话、多人协作、明确时限、依赖关系或后续复盘的工作。工单承载状态、负责人、输入物、交付物和决策记录。

不确定时交给总管判断。原则是让治理成本与任务风险匹配，而不是所有事情都建单。

5 · 常用任务流程

1
提出需求：说明目标和约束。总管或员工先确认理解。
2
确认方案：高影响或不确定工作先调研、给方案和取舍；你拍板后执行。
3
跟进进度：通过公司驾驶舱、团队看板、个人桌面或工单墙查看。补资料时说明对应任务，避免新建平行事实。
4
处理升级：遇到阻塞、冲突或需要用户决策时，系统按严重度和通知策略提示；你只需回答决策问题。
5
验收结果：明确说“通过”、指出返工项、暂停或取消。验收结论进入任务记录，机制负责校验账目一致性。
验收不通过：结论部分可以，但证据不足。请为三条结论分别补原始访谈引用，保留现有页面结构，明天 10:00 前重交。

6 · 你需要做什么

你负责
  • 说明真实目标、底线和优先级
  • 提供只有你掌握的资料和业务判断
  • 批准结构、制度、公开发布等高影响变更
  • 对最终成果验收
机制负责
  • 编号、结构和新增写入校验
  • 看板、索引、巡检和通知
  • 发现断链、异常状态和账目不一致
  • 保留可追溯事实并支持重建投影
机制能发现问题，但不会替你做业务取舍。低风险自动化可以自愈；涉及意义、授权和不可逆影响的事项仍由人决定。

7 · 常见情况怎么办

现象处理
会话没有加载正确身份或技能确认打开的是对应公司/团队/员工工作区；运行 doctor 查看锚和披露链接；必要时重新 bootstrap。
看板陈旧或同步失败确认本地 OPC 服务在运行；使用看板同步按钮或按 README 启动服务，再运行只读 verify。当前批次发布失败时，系统保留上一批可用数据；旧页面可能显示 legacy fallback 提示。
工单被标红标红代表实体能识别但字段不合法。打开详情修正状态、日期、引用或结构，不要删除记录来消除告警。
任务停滞、逾期或出现升级通知查看阻塞原因和需要你决定的事项；补资料、调整时限、换负责人、暂停或取消。
工单与 worklog 不一致让负责人按真实进度补账或修正状态。不要为了“看板好看”伪造完成记录。
想改员工、团队、项目目录名优先使用实体改名命令；手动改名后运行引用修复和链审计。--ensure-links 主要负责稳定锚、披露链接和规范链，不代替全部实体引用迁移。
换电脑或移动仓库重新运行 bootstrap/doctor，重建本机锚、钩子和服务自启；不要复制旧机器绝对路径配置。
不确定是不是机制问题把现象、操作步骤、实际结果和期望结果交给总管；先诊断，再决定是否修机制。

8 · 最小应急命令

日常使用通常不需要命令。以下命令只用于初始化和诊断：

python opc_resolver.py --bootstrap   # 首次初始化或环境重建
python opc_resolver.py --doctor      # 查看环境、锚、钩子、服务与治理检查
python opc_resolver.py --check       # 只检查命名空间和结构引用

Windows 通常使用 python，macOS/Linux 可能使用 python3。完整命令、服务启动和故障排查见 README.md；机制原理见 SYSTEM_GUIDE.html。

运行机制亮点 · 2026-11-09

变化不丢，批次可验

文件内容哈希识别快速修改和删除；手动、周期、监听共用生成锁。生成过程中源数据再变，则保留待重试状态。

状态说实话

本地看板成功与外部集成成功分别返回。私有资料缺席保留历史并标记未挂载，不伪造交付物。

发布有两道核验

共享策略按目录和实体 ID 过滤历史，随后逐历史树扫描；默认离线预览，显式发布才上传。工作仓库直推公开地址及其别名均拒绝。

服务有明确边界

HTTP 只提供看板白名单和 API，校验本机 Host。macOS launchd、Windows 启动文件夹和 Linux crontab 共用启动身份探活与超时策略。

本地备份以恢复校验为准，不能冒充异地备份；三平台测试矩阵与合成回归共同守住机制边界。
