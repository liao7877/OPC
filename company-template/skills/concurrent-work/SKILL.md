# 并发会话协作机制（concurrent-work）

> **一个会话 = 一个工位（seat）**。你的员工目录可能同时存在多个会话分身（多个工单并行、工单+直聊并行、总管子代理）。
> 本技能定义：怎么声明自己的工位、怎么知道别人在干嘛、谁有权改什么、怎么收口。全部是文件操作，零代码。
> **多开方式**：多开新会话由**用户手动开窗**（部分平台不支持程序自动新开同级会话）——用户对员工说"再开一个会话干 TSKyyy"即可，工位卡机制自动隔离互不干扰。

## 一、工位卡（每个会话启动必建）

会话开工动作（在启动流程里，紧跟读 AGENTS.md 之后）：

1. **建工位卡**：`workspace/sessions/seat-<HHMMSS>-<2位随机>.md`，内容：
   ```
   ---
   seat: seat-143052-07
   opened: 2026-08-28 14:30
   kind: 工单          # 工单 / 直聊 / 子代理 / 调度
   ticket: TSK00012     # kind=工单 时填；其他为空
   identity: 执行       # 执行 / 调度（总管自营单时标"执行"，见 §五）
   status: 工作中       # 工作中 / 已收口
   ---
   备注（做什么、预计多久）
   ```
2. **扫在岗分身**：列 `workspace/sessions/` 下所有 `status: 工作中` 的卡——
   - 有同工单的卡 → 你是协作者，看 §三；
   - 不同工单 → 各干各的，互不干扰；
   - 动手前做到心中有数，不抢活、不盲写。

## 二、权责划分（谁有权改什么）

| 资源 | 规则 |
|---|---|
| 工单 `task.md` | **持卡会话独占**：同一工单只有最先建卡且 status=工作中的会话可改 status/owner；其他会话是协作者 |
| 工单 `deliverables/` | 各会话中间产物先写自己 `workspace/sessions/<卡号>/scratch/`；**收口时由持卡会话合并**进 deliverables/（合并权唯一） |
| 工单 `messages.md` / `logs/` | 追加式，任何相关会话都可追加（只增不删） |
| `workspace/worklog.md` | 多会话可并发追加，**必须按追加协议**（见 worklog-discipline §五）：重读 → 在文件末尾补块 → 写临时文件 → 原子替换；写完自读校验，发现坏块立即补写 |
| `memory/MEMORY.md` | **并发会话一律不许直接写**。沉淀写 `memory/inbox/<卡号>.md`（自由格式，建议五要素）；**收口时合并**进 MEMORY.md 后删分片（合并前重读一遍最新版） |

**记忆归一规则（三处记忆的权威序，2026-08-28 定）**：

员工可积累记忆的位置有三处：实体记忆 `memory/`（权威）、平台记忆 `.workbuddy/memory/`（平台缓存）、会话即时上下文（易失）。规则：

1. **权威唯一**：对下次干活有用的长期经验（决策/结论/坑），**必须落在 `memory/`（经 inbox 收口合并）**——它是实体的一部分，换平台、换会话、换机器都在；
2. **平台记忆是缓存**：`.workbuddy/memory/` 里的有价值条目（如调度铁律、用户纠正记录），**收口时回写**进 memory/inbox → 合并进 MEMORY.md；只留在 .workbuddy 的经验视为未沉淀（换平台即失）；
3. **禁止反向**：不要把 memory/ 的内容复制成第二份放 .workbuddy 当"备份"——一份真相，引用即用。

> 员工换平台接入（如 WorkBuddy → Claude Code）后开工第一件事：读 `memory/MEMORY.md` 恢复长期记忆；发现 .workbuddy 有未回写的经验 → 先沉淀再干活。
| 私有 skills/、AGENTS.md | 单会话操作；另一个会话正在改的标志 = 存在 kind=工单且备注提到改技能的工作中卡片，此时先等或换会话 |

## 三、多会话共干同一工单

1. 后来者建卡时发现同工单已有持卡会话 → 自己的卡备注写"协作者"；
2. 协作者：不改 task.md 状态、不往 deliverables/ 直接写；产物进自己 scratch/，结论追加 messages.md；
3. 持卡会话收口时：读取各协作者 scratch + messages，合并出最终交付物 → deliverables/，然后按 ticket-system 走状态机；
4. 协作者卡在本会话结束时改为"已收口"（产物已交持卡人）。

## 四、直聊会话的边界（工单会话 + 直聊并行时）

直聊会话（用户直接找你聊小事/问进度）**三不碰**：不碰任何 task.md、不碰 MEMORY.md、不碰别人工位卡的 scratch。
只做两件事：worklog 追加（type: 直聊，按追加协议）+ 有沉淀写自己 `memory/inbox/<卡号>.md`。
聊出大活（值得建单）→ 按 ticket-system §1 号池取号建单，本会话升级为工单会话（更新工位卡 kind）。

## 五、总管自营单（总管被派活给自己）

1. 照常建单走完整状态机（owner: E0000 上板，不留暗账）；
2. 工位卡 `identity: 执行`——此时你以执行者身份干活，但**调度义务不停摆**：开工前先把该做的巡检做完（见 dispatch-sop），避免"总管忙自己的活、全公司失管"；
3. **不自审自批**：自营单进 review 后，验收人 = 用户或你指定的其他员工；不得自己把自营单改 done。

## 六、收口（每个会话结束必做）

按顺序：
1. **交付合并**（持卡会话）：scratch → deliverables/；
2. **关单/推进状态**（持卡会话）：按 ticket-system 状态机；
3. **memory 合并**：`memory/inbox/<卡号>.md` 若有内容 → 重读 MEMORY.md → 合并追加 → 删分片；
4. **翻转工位卡**：status 改 `已收口`（卡片文件保留，不删——历史工位审计）；
5. **汇报**：向派活方（总管/用户）一句话回报结果与交付物位置。

## 七、红线

1. 不删别人的工位卡；不改别人卡上的 ticket/status 字段；
2. 并发会话绝不直写 MEMORY.md（只走 inbox）；
3. 收口不完整就走人（卡停"工作中"、inbox 分片烂着）= 违规，下次会话启动发现遗留卡要上报总管；
4. 草稿不进 deliverables/（那是合并后的正式产物区）。

## 八、遗留卡处理（下次会话启动时）

扫到 `status: 工作中` 但明显已死（opened 超过 1 天、scratch 无近期改动）的卡：
1. 检查其 inbox 分片与 scratch 是否有价值；
2. 有价值 → 代为合并/收编，卡改"已收口"并备注"由 <你的卡号> 代收口"；
3. 无价值 → 直接翻"已收口"备注"判定废弃"；
4. 拿不准 → 上报总管裁决，不动文件。
