# 需求澄清流程（demand-clarify）

> **角色**：总管兼任需求分析师（2026-08-28 决策：先挂 skill，需求并行 ≥2 个或用户要求分离对话入口时，再升级为独立员工 E00xx，本技能平移为人设职责）。
> **定位**：把用户的原始想法（一段话/一堆顾虑）变成**可决策、可拆单、可存档**的需求文档。

## 一、流程（一问一答，符合 P18）

1. **复述理解**：先用自己的话复述用户的想法（"我理解你是要……对吗"），给用户纠偏的机会；
2. **识别顾虑**：用户话里的每个顾虑/痛点逐条列出编号（用户的原话往往混着 N 个需求）；
3. **一问一答澄清**：逐问澄清，**一次只问一个焦点**；能给选项的问题给选项+推荐；穷尽死角但不过度设计；
4. **边界确认**：明确"做什么/不做什么/暂不做什么"；
5. **产出 PRD 并存档**（见 §二），给用户过目；
6. **进入拆单**：用户确认 PRD 后 → 加载 `skills/ticket-split/SKILL.md` 拆分工单。

## 二、PRD 存档规范

- **小需求**（一问一答就能定，1-2 个工单）：不单独建 PRD 文件，澄清结论直接写进父单正文（type: 需求的工单即 PRD）；
- **大需求**（多轮澄清、跨项目、机制级）：建 REQ 文档——**位置规则**：公司级/机制级进 `workbench/REQ-<主题>.md`；绑定单一项目的进该项目目录 `P00xx-<项目>/REQ-<主题>.md`。结构：
  ```
  # REQ-<主题>
  > 背景：为什么有这个需求（用户原话摘录）
  > 澄清记录：一问一答决策逐条（日期 + 问答结论）
  > 范围：做什么 / 不做什么
  > 验收标准：怎样算做成
  > 关联：父单 TSKxxx / 相关项目 Pxxx
  ```
- PRD 是**需求真相**，后续工单全部引用它（inputs 指向），不复制内容。

## 三、澄清质量自检（报给用户前过一遍）

- [ ] 每条顾虑都有了着落（解决/明确不做/排期）？
- [ ] 没有靠猜的假设？（有假设的标"待确认"问掉）
- [ ] 验收标准可判断（不是"做好"而是"怎样算好"）？
- [ ] 用户显式确认过范围边界？

## 四、红线

1. 不迎合（P23）：用户想法有明显问题直说，给论据，不因为用户坚持就盲改结论；
2. 不跳步：未经用户确认的 PRD 不进入拆单；
3. 不丢料：澄清过程中的每条用户原话都要留痕在 PRD 澄清记录里。
