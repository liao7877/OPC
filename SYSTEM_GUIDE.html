OPC · 用 AI Agent 跑公司的组织级框架

OPC（Organization for AI-Agent Companies）把「一家公司」装进一个 Git 仓库：AI Agent 扮演总管和员工，文件系统是唯一真相，看板与报表只是可随时重建的投影。用户只负责提出构想，公司的运转、记录、巡检与异常告警由机制层与 Agent 自治完成。

零第三方依赖（纯 Python 标准库） Windows / macOS / Linux 三平台 CI 验证 26 条组织级设计原则 机制代码单例 · 公司目录零机制代码

一、它解决什么问题

问题

人管不住细节

AI 会话散落、结论不复用、改个目录名全文失效。OPC 用「文件即真相 + 符号化引用」把领域事实变成可版本化、可校验的资产。

问题

Agent 公司不自转

用户不来，公司就静止。OPC 给组织装了常驻后台中枢（OPC 服务）：数据一变即巡检 13 项（含工单逾期与停滞预警）、系统通知、待办闭环态、看板实时化——发现异常不依赖用户的注意力。

问题

多会话互相踩

多个 Agent 并发干活，谁改谁的文件？OPC 用工位卡划分领地、锁原语保护写路径、原子取号防撞号，把冲突面收敛到机制层。

二、一条主线：文件系统即真相

数据源（真相）task.md / worklog.md / roster.md / project.md
Agent 按纪律写入
→
生成层（机制）opc_tickets / opc_dashboards
OPC 根单例，校验+投影
→
展示层（投影）kanban / dashboard / teamboard / mydesk
只读，删了重跑即重建

数据流严格单向：展示层永不写回数据源。看板数据（*-data.js）不入库——clone 后跑一次 run_boards once 即重建，真相永不丢失。

三、目录即组织（实体即目录）

OPC/
├── opc.toml                 # 全局 manifest：路径唯一真相源 + 实体类型注册表 + 巡检/平台配置
├── opc_resolver.py          # 命名空间解析器（DI 容器）：opc:// 符号 → 物理路径
├── opc_tickets.py           # 工单看板生成器 + 建单（--auto-id 原子取号）
├── opc_dashboards.py        # 三级看板生成器（公司/团队/个人）+ 交叉核验
├── opc_service.py           # OPC 服务（常驻中枢）：看板实时化 + 巡检 13 项 + 通知 + 待办闭环
├── opc_patrol.py            # 巡检标准清单（服务内置调用；也可手动跑一次）
├── opc_schema.py            # 状态机与枚举唯一真相源（工单 7 态 / 巡检元数据）
├── opc_model.py             # 实体共享读取器 + 并发锁原语 + 技能索引生成
├── companies/C001/          # 稳定锚（junction/symlink）→ 真实公司目录，改名自愈
├── C001-AI自动化公司/       # 公司实例：总管 E0000 / 员工 E00xx / 团队 T00x / 项目 P00xx
│   ├── workbench/           #   工单系统：tasks/ 是真相，kanban.html 是投影
│   ├── skills/              #   公司级技能（三层技能体系：公司/团队/私有）
│   └── E0000/   #   ← 用户派活从这里进入（把它当工作区打开会话）
└── company-template/        # 开公司脚手架：create-company 技能一键拉起新公司

引用分两层：文档层用 opc://company:C001/... 逻辑符号（resolver 校验，pre-commit 拦截失效引用）；运行时层用 companies/<cid> 稳定锚（浏览器/脚本直开）。公司目录改名后跑一次 --ensure-links 即自愈，consumer 零改动。

四、机制亮点

命名空间

符号引用 + 稳定锚 + 自愈

  • 物理路径唯一真相源在 opc.toml，改名/迁移只动一处
  • 失效引用由 pre-commit / --doctor 拦截，绝不静默
  • 锚断了也能按 company.md 的「公司 ID」扫描发现自愈
质量门禁

init() 化的开工门禁

  • --doctor 七项自检：Python / 稳定锚 / 钩子 / 服务探活 / 命名空间 / 技能披露 / 模板 diff 与技能体量
  • Agent 开工前必过，不绿不许进业务
  • GitHub Actions 三平台 × 双 Python 版本矩阵持续验证
并发协作

工位卡 + 锁原语 + 原子取号

  • 一个会话 = 一张工位卡，领地清晰、收口合并
  • file_lock（O_EXCL + 超时 + 过期抢占）保护台账/建账等热写路径
  • --new --auto-id：目录存在性即锁，并发建单不撞号、自动占台账
公司自转

巡检 = 控制循环（reconcile）

AI 员工会漏接单、忘推进、改了 A 忘了 B——人盯人是盯不住的。OPC 借 Kubernetes 控制循环：先声明期望态，再周期观测实际态，diff 出偏差就修正或告警——公司自转不靠人盯。

  • 13 项期望态检查（数据一变即巡检，另有周期兜底）：阻塞解锁 / 认领缺口 / 双账 / 脱期事务 / 工单逾期与停滞预警 / 升级信箱 / 号池 / 知识库增量…
  • 发现新异常弹系统通知（只报新发现，不重复轰炸）；只有「升级信箱」是 critical 级，用户只被它打扰
  • patrol-state 闭环态：处置完置 handled，再犯自动重开——偏差处置本身也有状态机
  • 看板实时化：「同步」按钮直调生成器重算，数据刷新秒级生效
技能体系

三层技能 + 生成物索引

  • 公司级 / 团队级 / 私有三层，SKILL.md frontmatter 是元数据唯一真相
  • 触发词（triggers）结构化，--sync-index 生成各层 INDEX，「登记」动作消失
  • 渐进式披露：命中触发词才读全文，省 token
内容治理 P31

三问法归位 + 渐进式披露

  • 内容归位三问：跨公司→根层一份；公司政策→公司层正文、他层只留一行引用（opc:// 链接 + 为什么读）；单角色→员工技能
  • 写规范类内容「精准高效、本质而非肤浅」——每句话要么改变行为要么帮助定位；例外：记忆/日志等事实记录类细节优先不精简
  • SKILL.md 正文是「路由器」不是百科（≤120 行，doctor 门禁检测）：模板/告警对照/示例拆 Level 3 附属文件按需读，打样 ticket-system 258→80 行、presales 260→64 行
安全边界

最小写边界 + 并发收口

  • 只读 API + 唯一写动作 POST /sync（同源校验，same-site 也拒）；静态服务双重防目录穿越（双分隔符切段 + realpath 兜底）
  • 巡检三触发源全程持每公司锁；atomic_write 唯一 tmp 名防双写者互踩；watch 生成期间对监听不可见，不重复重算
  • 服务异常不静默：后台循环错误记入 last_error，/api/ping 可查
扩展性

实体注册表 + 开司脚手架

  • [entity_types]：加新实体类型 = manifest 加一行，五处消费方自动跟随
  • create-company 技能按模板一键开新公司，机制零复制
  • --diff-template 双向 diff 防模板与实例漂移
设计借鉴

站在六十年沉淀上偷师

这套系统的很多设计不是拍脑袋，是站在计算机科学六十年沉淀上偷的师——但 AI 组织的「硬件」是人、文件和会话。

  • 技能三层渐进披露 = CPU 多级缓存（L1 元数据常驻 / L2 正文按需 / L3 附属文件冷存）
  • opc:// 符号引用 + 稳定锚 = 虚拟内存寻址（resolver 是 MMU，公司改名 = 页表重映射）
  • 决策 #18 收敛单服务 = 微内核化
  • 巡检 = 控制循环（Kubernetes reconcile）
  • 升级超时升层 = 断路器
  • 台账先占号后建单 = 写前日志（WAL）

每条映射的设计动机详见仓库 PRINCIPLES 与机制文档（设计借鉴手册沉淀中）。

五、容错哲学（P11）

跳过 + 告警

坏数据跳过并告警，绝不静默降级污染结果，也不一票否决整体。

上板标红

status 非法的工单不消失——独立成列、红色渲染，修好后恢复。坏数据必须「看得见」。

交叉核验

worklog 双账与工单状态逐条核对；失效引用、死链、陈旧数据全部主动暴露。
