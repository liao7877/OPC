01 · 为什么需要 OPC

一个聊天窗口能完成一件事，但一个组织要在很多天、很多会话、很多角色之间持续可靠地完成事情。

先用一句话理解聊天像口头吩咐，组织需要的是一本能被不同人和不同工具共同读取的账本。

会话会消失

今天打开的 Agent 明天可能关闭。任务不能只放在上下文里，必须放进下一次会话仍能发现的文件。

规则会复制漂移

把同一条规则复制到总管、员工、团队和模板，修改一次就可能漏掉另一份。

责任会变模糊

“有人在做”不等于“谁负责、做到哪、何时验收”。组织需要可追溯的 owner、状态和交接。

知识会腐烂

对话里的经验难复用，公共库里的材料难定位；没有归属和复核机制，越积越不可信。

自动化会静默失败

程序遇到坏日期、断链或非法状态时如果悄悄忽略，仪表盘上的“正常”反而最危险。

物理环境会变化

公司目录可能改名，仓库可能搬家，系统可能从 Windows 换到 macOS。物理路径不应该成为组织关系本身。

OPC 的回答把组织能力拆成可验证的不变量：事实只有一个来源；身份有稳定 ID；引用走逻辑地址；写入有边界；投影可以重建；异常必须有等级和证据；机器发现问题，人决定意义。
项目价值OPC 把原本只存在于人脑、提示词和临时会话里的组织能力，变成可审计、可迁移、可复盘、可扩展的本地系统资产，同时避免把每家公司都做成一套分叉代码。

02 · 用五个对象看懂全系统

先不要记命令。把 OPC 想成一家公司：用户提出意图，Agent 办事，文件保存事实，服务值班，页面展示结果。

对象一：用户意图

需求不是一句漂亮话，而是目标、范围、资料、验收和时限。缺信息可以先澄清，不能靠猜。

对象二：Agent 会话

Agent 是执行者，不是组织真相。会话可以短暂，角色规范和任务记录不能短暂。

对象三：领域文件

工单、worklog、roster、知识和制度保存可审计事实；它们可以被 Git 版本化。

对象四：机制内核

resolver、门禁、锁、取号、服务和巡检把“应该怎样”变成可检查行为。

对象五：投影

看板、INDEX、通知和 API 为发现服务。投影损坏时，应能从领域文件重建。

研发者展开：四种数据角色
角色例子是否权威失败处理
写模型task.md、worklog.md、roster.md是门禁、锁、人工修正
派生模型INDEX.md、tasks-data.json否校验后重建
运行状态patrol-state、pending、服务心跳仅对运行过程可重建、可过期
解释文档SYSTEM_GUIDE、README、PRINCIPLES各自有职责以代码契约和 canonical skill 校准

03 · 目录结构：每个目录回答一个问题

目录不是收纳习惯，而是组织模型。目录的位置表达“谁拥有它、它服务什么生命周期、能不能重建”。

位置它回答的问题维护者能否重建
opc.toml物理路径和注册表怎样映射到逻辑名称？机制维护者不能盲目自动生成，需审阅
company.md/roster.md公司是谁、谁属于哪个团队？公司/总管事实不能由看板反推
AGENTS.md这一层的规范入口和直属上级是什么？对应层级规范链声明可派生
task.md/worklog.md组织承诺什么、实际推进了什么？负责人/员工不能用投影替代
INDEX.md/*-data.js如何快速找到事实？生成器/服务可以删除后重建
重要边界companies/<CID> 是稳定锚，不是第二份公司副本。真实目录改名时重指向锚；不能同时维护锚和实例两份正文。

04 · 身份、规范链与 opc://：名字可以变，身份证不能乱

生活类比门牌可以换，身份证号不应跟着换。目录后缀给人读，实体 ID 给机器认。
实体规则公司、团队、员工、项目、工单等都是实体。目录名采用“稳定 ID + 可读说明”，例如 E0007-AI员工-前端工程师。机器使用 E0007，人使用后缀；改名不应改变实体身份。

逻辑地址和物理地址

直接写 ../../C001-AI自动化公司/E0007...，等于把门牌地址写进所有通讯录。OPC 使用 opc:// 逻辑地址：

opc://company:C001/skill/ticket-system/SKILL.md
opc://company:C001/workbench/tasks/TSK00010-E0001分析员改名售前工程师并赋能售前技能/task.md
opc://org/PRINCIPLES.md

opc_resolver.py 是地址簿：读取 opc.toml 和公司事实，把逻辑地址解析为当前机器上的路径。解析失败必须明确抛错；越界、歧义、断链不能“猜一个能用的路径”。

研发者展开：解析器的安全不变量
  • manifest 的公司 home、key、实体 ID 和子路径必须落在允许的公司根内。
  • 使用真实路径 containment 检查，而不是字符串前缀；Windows 盘符、UNC、反斜杠和符号链接都要纳入判断。
  • roster 可以声明多个团队；当前规范链选择第一项有效团队作为直属链，同时报告多团队提示，避免假装支持未定义的多继承冲突规则。
  • 稳定锚的作用是承接物理迁移，不是绕过权限或隐藏错误。

05 · Agent 如何引用规范和技能

“规范链”“技能披露”“平台钩子”是三个不同问题：谁应该遵守、哪里有能力、平台如何把文件交给会话。

AGENTS.md：应该遵守什么

身份、职责、红线、直属上级和技能入口。它不是百科，也不是所有操作步骤的复制品。

SKILL.md：怎样完成一类工作

技能包含触发词、流程、模板、验收和边界。命中后按需读取，细节放 reference。

INDEX.md：怎样快速找到

技能和知识索引是生成物。它减少“全目录翻找”，不取代 frontmatter 和正文真相。

平台适配：怎样被看见

WorkBuddy junction、Claude/Codex 的 hook 和平台原生加载负责接入；平台差异集中在接入层。

不要混淆技能是“完成工作的方法”，制度是“持续生效的组织约束”。需要每次都遵守的红线不能只放在一个可能没被触发的技能里。

06 · 知识、记忆与组织学习

生活类比日记、百科、操作手册和公司制度不是同一种书。把它们全塞进一个目录，搜索和责任都会失真。
层次回答什么问题典型位置处理方式
memory这个角色最近经历了什么？员工 memory时序事实，私有、细节优先
knowledge组织已经知道什么？员工/团队/公司 knowledge三级同构，索引→摘要→全文
method怎样稳定完成一类工作？方法条目、技能 reference提炼后复用，保留来源
policy组织要求所有人怎样做？制度、AGENTS、原则规范化、可检查、不能只靠触发

两条轴，不要混成一条

归属轴

员工、团队、公司决定知识放在哪一级；越近越具体，越上浮越公共。

硬度轴

经验、方法卡、技能、制度决定知识稳定到什么程度；稳定性提高要经过复盘和审批。

上浮原则上浮是归属转移，不是复制。目标层保存唯一正文，源位置保留一个真实存根承接旧 opc:// 引用；索引由机器重建，结构变更默认需要人授权。

知识飞轮

  1. 经历：任务、对话或 worklog 产生事实。
  2. 留痕：把关键结果和证据写进实体记录，而不是只留在会话上下文。
  3. 提炼：从一次性事实中识别可复用方法，保留原始来源。
  4. 审核：判断它是否足够普遍、稳定、无敏感信息。
  5. 归位：进入员工、团队或公司知识层，必要时晋升为技能或制度。
  6. 复用：通过索引和触发词按需加载，再在新任务中验证。
研发者展开：为什么不自动删除和自动晋升

引用次数只能近似表示“被文档引用”，不能证明 Agent 真的读过或业务仍需要。自动删除会破坏历史证据；自动晋升会把一次偶然结论伪装成组织规则。因此机器只负责发现过期、零命中、疑似重复和结构漂移，处置由人决定且应可逆。

07 · 工单、事务与 worklog 双账

工单是组织对“要交付什么”的承诺；worklog 是员工对“实际推进了什么”的流水。两者有关，但不是同一份数据复制两遍。

直聊车道

问答、一次性小改、无需独立验收和交接的工作。关键结果仍按纪律留痕。

工单车道

需要验收、跨会话、多人协作、时限、依赖或复盘的工作。目录中的 task.md 是事实。

事务车道

没有明确终点但需要周期推进的事情，例如维护、复核、内容更新。通过 AFF 和 worklog 形成节奏。

一张工单里有哪些事实

字段/文件作用为什么不能只写在对话里
id/title/owner身份、目标、责任不同会话需要同一称呼
status/due/priority当前状态、时限、取舍便于巡检和排序
blocked_by/parent依赖和父子闭环防止“看似进行、实际被锁死”
inputs/deliverables输入和交付物地址让验收有证据，不靠记忆
messages/logs澄清、交接、执行轨迹跨会话复盘不丢上下文

双账如何交叉核验

失败可见缺 frontmatter、无法解析的文件跳过并告警；实体可识别但字段非法时保留投影、标红并告警。这样错误不会污染正常统计，也不会从系统中无声消失。

08 · 原子写、锁与故障恢复

先分清两个概念原子写解决“读者不要看到半个文件”；锁解决“两个写者不要依据同一旧快照互相覆盖”。它们不是一回事。

atomic_write

先写唯一临时文件，再用 os.replace 替换目标。目标读者看到的是旧文件或新文件，不是半截文件。

file_lock

用跨进程锁保护读→改→写。锁包含 PID、token、取得时间和 heartbeat；活进程不能仅因 mtime 过期被抢。

worklog canonical lock

同一员工的热账、归档账、自动建账和 append 使用同一把 workspace 锁，统一分配 wid。

工位卡

锁只保证文件互斥，工位卡表达“哪个会话负责当前工作”。语义所有权不能只靠 OS 锁。

知识上浮为什么需要 journal

上浮涉及目标写入、源替换、存根和索引，跨多个文件。journal 保存 source/destination、内容 hash 和阶段：

prepared → dest_written → source_stubbed → indexes_synced → committed

如果进程在中间退出，下一次操作先读取 journal，只按 hash 前滚。目标或源被人改过而 hash 不匹配时，保留 journal、报告冲突，绝不覆盖新事实。这是“小型事务日志”，不是把整个 OPC 变成重型数据库。

边界上述锁只约束遵守 OPC 写入口的写者。用户直接用编辑器裸改文件仍可能绕过锁，因此巡检和校验仍是第二道防线；网络共享盘也不一定提供与本地文件系统相同的 rename/O_EXCL 语义。
研发者展开：故障矩阵
故障点允许留下什么下一次如何处理
目标写之前journal=prepared补写目标，前提是源 hash 未变
目标写之后目标正确、源仍原文写存根并继续
源替换之后目标正确、源为存根重建索引并提交
发现未知 hashjournal 保留停机报告，人工合并

09 · 看板投影与批次发布

机场屏幕不是航班本身。屏幕坏了可以从航班记录重建；但同一位旅客不能同时看到来自三套不同航班表的拼接结果。

旧问题逐个替换 tasks、dashboard、teamboard、mydesk 文件，即使每个文件本身完整，进程中断仍可能让用户看到新工单配旧个人桌面。
新机制每次生成先写到 staging，完成后形成不可变 release；manifest 记录批次、CID、来源指纹、每个 artifact 的 hash 和大小；最后只原子替换一个 current.js 指针。

一次发布的顺序

  1. 获取公司级跨进程发布锁。
  2. 给输入文件计算排序后的 SHA-256 source fingerprint。
  3. 生成全部投影到 staging，不直接改活文件。
  4. 验证 manifest、路径 containment、文件 hash、CID 和批次。
  5. 将 staging 原子重命名为 release。
  6. 原子更新 current.js；失败则旧批次继续服务。

兼容迁移

当前旧的固定 *-data.js 文件仍可作为 legacy fallback，保证 file:// 双击打开不突然失效。新页面和 API 逐步读取 current/release；兼容期必须明确显示“legacy fallback 不保证全批次”，不能静默假装已经原子发布。

研发者展开：为什么用 manifest 和 hash

时间戳只能说明文件大概什么时候写过，不能证明两个文件来自同一轮生成。batch_id 表示生成轮次，source_fingerprint 表示输入快照，artifact hash 表示发布内容未被篡改。它们分别解决“同批”“同源”“未变”三个问题。

10 · 服务、巡检与通知：把组织做成控制循环

OPC 服务像夜班值守，不是老板，也不是远程数据库。它观察文件、执行校验、重建投影、发送提醒，然后把需要判断的事交还给人。

服务监听什么

任务、worklog、roster、知识和模板的变动；周期兜底防止 mtime 或外部写入遗漏。

巡检发现什么

未认领、阻塞、逾期、停滞、双账不一致、依赖环、陈旧投影、知识腐烂和升级信箱。

通知如何克制

按 critical/warn/info 去重；勿扰和不在场模式影响普通提醒，真正紧急事项仍需可达。

服务不做什么

不替用户批准制度，不自动删除知识，不凭看板写回事实，不把单机服务伪装成集群。

三类结果error 代表机制无法可信工作，应阻断；warning 代表业务需要人处理，不应让整台组织停机；info 代表可选优化。SessionStart 可以提示但保持平台兼容，真正硬阻断落在 doctor、pre-commit、CI 和严格 verify。

11 · 在线协作与 Level 3 同步

飞书、钉钉等在线平台是员工的协作工具；OPC 仍负责身份、治理、正式工单、worklog、正式知识和审计。Level 3 不是把两边全文复制，而是让每个资源有明确权威、稳定绑定、冲突和可追溯同步。

Skill 决定怎样做

飞书多维表格与知识 Skill 规定可读/可写范围、确认边界、外部内容不可信和本地留痕。

CLI/HTTP 负责动作

优先使用可核验 CLI 或官方 HTTP API；MCP 只在已配置、已授权且 CLI/HTTP 不适用时作为 fallback。

Binding 建立身份

本地逻辑 ID 与外部 app、table、record、document 的稳定 ID 绑定；标题和 URL 不能单独充当身份。

Shadow 进入看板

外部任务标准化后进入公司驾驶舱的在线协作区，但不伪装成本地 task.md，也不进入本地完成率。

五个核心对象

对象作用关键边界
authority声明整个资源或字段由本地还是在线端负责未声明不写回，不使用静默 last-write-wins
binding连接本地实体和外部稳定 ID包含方向、字段 policy 和最近检查点
shadow保存外部资源的标准化只读影子不保存第三方 prompt 为指令，不自动创建本地工单
conflict双方变化、版本竞态或字段歧义暂停覆盖，进入 #18 巡检，等待人裁决
tombstone记录外部或本地删除事实先保留墓碑，不自动传播硬删除

飞书第一版的真实能力

当前适配器通过标准库 HTTP 调官方开放平台：支持 tenant token、多维表格分页/单条读取、字段白名单的单条更新，以及 Wiki/DOCX 只读。飞书更新接口没有公开 If-Match/ETag 条件写，OPC 因此在单表写锁内先回读，以字段内容 hash 做应用层 expected version；它能发现大多数竞态，但不能冒充平台提供的强 CAS。删除、批量修改、字段结构和权限变更默认关闭。

研发者展开：状态和持久化

opc_integrations.py 定义平台中立模型和 Connector 契约；opc_sync.py 使用 .opc-sync/state.json、events.jsonl 和 projection.json 保存绑定、shadow、冲突、墓碑与事件；integrations/feishu.py 只处理飞书 HTTP 边界；integrations/feishu_connector.py 将多维表格映射为统一 Connector。状态文件是本机运行态，不存 app secret。

运行机制亮点 · 2026-11-09

变化不丢，批次可验

文件内容哈希识别快速修改和删除；手动、周期、监听共用生成锁。生成过程中源数据再变，则保留待重试状态。

状态说实话

初始化子步骤失败会保留错误并返回非零，避免把未完成的自举报为全绿。

本地看板成功与外部集成成功分别返回。私有资料缺席保留历史并标记未挂载，不伪造交付物。

发布有两道核验

共享策略按目录和实体 ID 过滤历史，随后逐历史树扫描；默认离线预览，显式发布才上传；上传前锁定远端版本，发生并行提交则拒绝覆盖。工作仓库直推公开地址及其别名均拒绝。

服务有明确边界

HTTP 只提供看板白名单和 API，校验本机 Host。macOS launchd、Windows 启动文件夹和 Linux crontab 共用启动身份探活、单实例锁与超时策略。

本地备份以恢复校验为准，不能冒充异地备份；三平台测试矩阵与合成回归共同守住机制边界。

12 · 错误、安全、隐私与跨平台

错误不是失败，静默才是

输入情况处理原因
缺文件、缺 frontmatter、无法解析跳过并告警避免坏结构污染正常投影
实体可识别但 status/date 非法保留、标红、告警不能因为字段错就抹掉事实
路径越界、命名空间断链失败并阻断这是安全边界或身份关系错误
业务巡检发现逾期/阻塞通知并生成待办这是管理问题，不是生成器崩溃

读宽写窄

只读 API 让 Agent 和页面容易发现状态；写动作集中到明确的 POST /sync 和受门禁保护的文件写入口。路径参数必须经过租户 containment；输入物链接只允许 workbench 内相对路径，不能把 javascript: 或 ../../ 变成可点击地址。

公开发布不是普通 push

工作 main 可能含私有内容，私有 backup 保存全量；公开远程只能接收经过私有清单剥离的干净子集。发布应保留来源、revision、剥离清单和审批证据。历史重写不能让已经泄露的凭据重新安全，泄露后仍需轮换。

三平台的共同契约

层共同要求平台差异
路径使用 resolver 和 Path API，拒绝裸组织路径Windows 盘符/反斜杠；Unix 分隔符
稳定锚companies/<CID> 承接逻辑地址Windows junction；macOS/Linux symlink
自启同一个前台服务契约Windows 启动文件夹、macOS launchd、Linux crontab
验证Python 3.11+、selftest、doctor、CICI runner 和 shell/PowerShell 语法
明确限制OPC 是本地优先的组织框架，不是强一致多机数据库、细粒度远程权限系统，也不承诺在网络共享盘上复制本地 rename 和锁的全部语义。

13 · 思想来源、端到端案例与边界

设计借了什么

来源思想借鉴不照搬
单一真相 SSOT文件是事实，投影可重建不把每个索引都当第二真相
DIP/Repository业务消费者依赖 resolver/模型接口不让每个公司复制机制代码
虚拟内存/MMU、DNS逻辑地址与物理位置分离不把类比误当权限系统
缓存与渐进披露INDEX/摘要常驻，正文按需读不缓存过期事实而不校验来源
WAL 与文件锁写前记录、原子替换、崩溃可恢复不为简单文件 CRUD 引入重型数据库
Kubernetes reconcile期望态、观测态、幂等收敛不让控制器代替业务审批
CQRS/物化视图写模型与读投影分离，批次可验证不强行把所有历史变成事件溯源系统
GitOps/策略即代码版本化、漂移可见、规则可检查不把合并自动等于授权发布

端到端案例：网站改版

  1. 用户对总管说：“请在两周内完成官网改版，重点提升线索转化，给我可验收页面和数据依据。”
  2. 总管澄清目标、资料、范围、验收和 due，建立父工单；前端、内容、测试拆成子单，依赖关系写入 blocked_by/parent。
  3. 员工会话按规范链读取根、公司、团队和岗位入口；命中“页面开发”技能后才读完整流程和参考资料。
  4. 负责人认领后在 worklog 记录计划、进行和完成；工单状态与 worklog ticket 交叉核验。
  5. 并行会话通过 workspace 锁和原子取号写入，避免 wid 撞号；交付物使用安全相对路径。
  6. OPC 服务发现数据变化，生成同一批次的工单和公司/团队/个人投影；巡检发现测试子单未完成就告警。
  7. 用户在 review 阶段检查页面、证据和验收标准；不通过就给具体返工条件，通过才进入 done。
  8. 复盘结论先留在项目事实，再判断是否上浮为团队方法；稳定且普遍的做法才进入技能或制度。
  9. 公开发布时把客户私有资料加入剥离清单，生成干净子集并保留发布证据。

适用与不适用

适合

本地优先、需要多个 AI 角色协作、希望文件可审计和 Git 可版本化、组织规模中小、仍有人做关键决策的团队。

不替代

高吞吐交易数据库、跨地域强一致系统、复杂 RBAC/合规权限平台、无人监管的全自动经营系统。
