OPC · Organization for AI-Agent Companies

用 AI Agent 跑一家公司，
组织本身也要有一套「操作系统」

你雇了一群 AI 员工（总管、售前、项目经理），把公司目录当工作区打开就能派活。但让几个 AI 稳定协作，靠的不是把提示词写得更好，而是给组织本身配上机制：文件即真相、目录即组织、巡检即管理、门禁即纪律。这份文档讲清楚这些机制从哪来、为什么这样设计——它站在计算机科学六十年的沉淀上。

01
问题定义

它解决什么问题

AI 员工单兵能力很强，但「一群 AI 组成的公司」会患上三种组织病——每一种都真实发生过。

组织病一：活儿没人接，接了没人推

痛点总管派了一张工单给售前工程师，售前的会话恰好没开。这个活就静静躺在目录里——没有提醒、没有超时、没有兜底。三天后你想起来问进度，谁都不记得有这单。人类公司靠例会和经理盯，AI 会话今天开明天关，例会根本开不起来。

组织病二：同一条规则，三份版本

痛点「工单怎么建」写进了总管的 SOP、售前的技能、项目经理的笔记。半年后机制升级了，三处只改了两处。新员工读到旧版，建出来的单看板不认——没人知道哪份是真的，因为真相不止一份。

组织病三：改了机制，没人知道，也没人能验证

痛点你让 AI 改了一处生成器逻辑，它说「改好了」。改的对不对？别的公司会不会被影响？Mac 上还能跑吗？下个月你自己都忘了当初为什么这么改。组织记忆随着会话结束而蒸发。
机制OPC 的回答不是「加强提示词」，而是把组织搬到一套有纪律的机制上：文件系统即真相（02）让状态可见可审计；实体即目录（03）让身份不漂移；符号引用 + 稳定锚（04）让改名不断链；门禁 + 自检（05）让每次改动都被机器验证；技能分层（06-07）让知识单一真相；常驻服务 + 巡检（09-10）让组织自己发现漏接、逾期、失账——人只被真正需要决策的事打扰。
落点一句话：OPC = 给「AI 员工组成的组织」装上操作系统级的机制层——调度、内存管理、中断、文件系统，一样不少，只是硬件换成了人、文件和会话。
02
主线设计

一条主线：文件系统即真相

整个组织没有任何私有数据库、私有服务端——所有状态都是你硬盘上的纯文本文件。

痛点常见的协作工具把状态藏在数据库里：任务在 Jira 的服务器上、知识在 Notion 的云端、流程在某个 SaaS 的后台。你想查「这单为什么黄了」，要在五个系统里跳；想回滚一个错误变更？对不起，没有版本历史。
机制OPC 反其道：工单是 task.md、员工档案是 roster.md、工作记录是 worklog.md、巡检结果是 patrol-log.md。生成器读这些文件算出看板数据，看板只是投影。文件是唯一真相，看板、报表、API 全是只读投影。
落点三个白赚的好处：① git 天然接管审计与回滚——任何变更可追溯、可撤销；② file:// 双击即开——看板不依赖服务器也能看（服务在线时自动实时化）；③ 任何编辑器、任何 agent 平台都能操作——不锁定任何工具生态。代价是我们必须自己解决数据库本可以替我们解决的问题：并发锁（08）、缓存一致性（06）、数据校验（11）——这正是机制层存在的意义。
03
组织结构

目录即组织（实体即目录）

公司、团队、项目、员工、工单——每个组织实体就是一个目录，目录名就是身份证。

痛点组织架构记在聊天记录里：「售前工程师是谁来着？上次那个项目叫什么编号？」——问 AI，它要去翻十天前的会话；人入职离职、项目开结，状态散落各处，组织结构图永远过时。
机制实体即目录，ID 唯一真相：
  • C001-AI自动化公司/ —— 公司（C = Company）
  • T001-AI开发团队/ —— 团队（T = Team，内含 teamboard 团队看板）
  • P0004-公司看板与工作记录系统/ —— 项目（P = Project，归属用 team 字段声明）
  • E0001-AI员工-售前工程师/ —— 员工（E = Employee，内含 worklog 工作日志、mydesk 个人看板）
  • workbench/tasks/TSK00010-搭建日志系统/ —— 工单（一单一目录，task.md 是全部事实）
决策 #17：目录名 = ID-说明后缀——ID 是机器的唯一真相，后缀是给人看的显示名，一个名字同时服务两个读者。
落点实体注册表（opc.toml [entity_types]）是前缀的唯一真相：加一种实体类型（比如「客户 CUST」「供应商 SUP」）= manifest 加一行，resolver、生成器、巡检、结构自检五处消费方自动跟随，零代码改动。开新公司 = 复制模板目录 + 填 company.md，脚手架技能一键完成。
04
组成原理 · 虚拟内存

opc:// 寻址：给组织装一套 MMU

全仓库几十万字的文档互相引用，凭什么公司改名、目录迁移不断一根链？

痛点文档里写满相对路径：../../companies/C001/workbench/...。哪天你把公司目录改个名、或者把仓库挪个地方，几百处引用集体断掉——而且断得悄无声息，文档照常显示，点进去 404。
机制借鉴虚拟内存：应用程序只用虚拟地址，物理内存怎么布局是操作系统的事。
  • 虚拟地址 = opc://company:C001/skills/ticket-system、opc://org/PRINCIPLES——文档里只写符号引用，禁止裸相对路径（P26）
  • MMU/页表 = opc_resolver.py：符号地址 → 物理路径，唯一翻译入口
  • 物理帧 = 稳定锚 companies/C001（Windows junction / macOS·Linux symlink）——真实目录变了，锚重新指向即可
  • 页表重映射 = 公司改名后跑 --ensure-links，全组织引用零改动
  • 缺页检测 = --check / pre-commit / doctor 全文扫描 opc:// 引用，失效即拦截，绝不静默；断了还能按 company.md 的「公司 ID」现场扫描自愈
落点这不是为了炫技：它让「组织结构可演化」成为常态——改名、迁移、重构在 OPC 里是低风险操作，因为物理布局从一开始就不进文档。
05
软件工程 · init 与 CI

开工门禁：把系统初始化做成 init()

任何一个 AI agent 在这个仓库开工前，都必须先过一道机器自检——全绿才许进业务。

痛点新 clone 一个仓库，「能跑」全靠口口相传：要先装钩子、要建链接、要生成看板数据、Python 版本有要求…… agent 开工时这些全靠它自己想起来，漏一步就是各种诡异报错。更糟的是：上一手留下的坏引用、断掉的锚，没人拦。
机制把初始化收敛成一个函数调用 python opc_resolver.py --doctor，七项自检 + 自愈：
  • Python 版本 ≥ 3.11、稳定锚存在且指向有效、pre-commit 钩子已装
  • OPC 服务探活（HTTP /api/ping 实测，不轻信端口占用）
  • 命名空间全文扫描（所有 opc:// 引用可解析 + SKILL.md 相对链接断链校验）
  • 技能披露链接完整、实例↔模板 diff 无未登记差异、技能体量达标（P31）
  • 自愈先行：缺锚、缺链接、缺看板数据，检查前自动补齐（打印 [fix] 行）——新 clone 跑一次 doctor 即完成自举
兜底是 python opc_resolver.py --bootstrap 一键自举（链接 + 钩子 + 数据 + 索引 + 服务自启）。背后还有 GitHub Actions 三平台 × 双 Python 版本矩阵 + 七个模块内置 selftest，每次提交全量验证。
落点「门禁即跨平台验收」：doctor 全绿 + selftest 全绿 + CI 矩阵全绿，才算改完。agent 的开工仪式和函数初始化一样可靠——这就是把 P30（三平台承诺）从口号变成每次提交的机器验证。
06
组成原理 · 多级缓存

技能体系：给 agent 的知识装上多级缓存

一个售前技能 260 行，十五个技能全塞进会话？agent 的「寄存器」当场爆掉。缓存分层是唯一解。

痛点最常见的失败模式：把方法论、模板、告警对照、书单全部写进一个 SKILL.md，认为「写全才专业」。结果每次触发加载 260 行，其中这次任务用得上的不到 30 行——贵、慢，而且长上下文会稀释模型对关键规则的注意力。反过来，全部外链则 agent 每次都要猜该读哪个文件。
机制渐进式披露（Anthropic Agent Skills 的官方设计），像 CPU 缓存一样分层，越热的层越小越快：
L1 · 常驻name + description + triggers只有技能名和触发词进系统提示，每技能约一行；agent 靠它判断「这个场景该用哪个技能」
→
L2 · 按需SKILL.md 正文命中触发词才整篇加载。定位是路由器不是百科：只写规则主干，≤120 行（doctor 门禁检测超限）
→
L3 · 冷存附属文件PRD 大模板、19 类告警对照、书单、新手示例——正文给链接，用到才读，读了不亏
→
磁盘archive/ 归档历史过程文档冷热分层，绝不占缓存
落点打样实证：ticket-system 258→80 行、售前技能 260→64 行（-75%），规则一条没丢，细节全部下放 L3。三个配套纪律：① 正文 ≤120 行进 doctor 门禁，防止将来写肿回去；② description 只写「何时触发」，不复制内容摘要（那是 L1 重复 L2）；③ 技能/索引变更后必须提醒重开会话——会话里的技能列表是启动时的快照，这是已知的缓存一致性行为（缓存失效纪律，见 dispatch-sop）。
07
内容治理 · P31 三问法

内容归位：一份知识到底放哪？

同一条规范被复制进三个员工的技能，半年后三处三个版本——治理知识的第一步是决定它住在哪。

痛点AI 写文档的通病是「太具体、太片面、到处复制」：为了自包含，每个技能里都塞一份背景；为了安全，每层目录都放一份规则。结果是组织知识大爆炸，真相却在复制中漂移。
机制写任何内容前过四问，落位唯一：
① 跨公司成立？换一家公司这条内容还成立 → 根层一份（如 create-company 技能、PRINCIPLES 原则）
→
② 多角色纪律？公司政策、多个角色必须动作一致 → 公司层正文；其他层只留一行引用（opc:// 链接 + 一句为什么读）
→
③ 单角色手艺？只有一个角色执行 → 该员工的 skills/，且一技能一触发场景（巨型技能 = 缓存污染）
→
④ 跟实体走？属于某项目/工单/人的生命周期 → 实体目录（事实记录，细节优先）

配套判据（SOP 归位实战沉淀）

判据内容
纪律 vs 手艺「大家动作不一致协作就断」→ 公司级纪律（如 ticket-system）；「某角色干得好不好的方法」→ 员工手艺（如 presales）。判例：公司级四技能全是纪律，总管五技能全是手艺。
最小公共上浮执行者跨 N 个角色 → 放最小公共层。上浮有成本：加载者变多、审批链变长——没有真实复用就不上浮（类比缓存上浮：没有命中率不往 L1 推）。
参数回机制层SOP 正文出现具体参数值（「14 天未动算停滞」）= 双真相警觉：阈值真相在 opc_schema，文档引用不复制。
表达总纲写规范/原则/技能类内容：「精准高效、本质而非肤浅」——每句话要么改变行为、要么帮助定位。例外：记忆/日志/worklog/messages 等事实记录类，细节优先不精简（P31 例外条款）。
落点约束不靠自觉：doctor 门禁检测正文超限（机器发现、人工决策），模板与实例的一致性由 diff-template + 已知差异登记清单管理；纪律类技能真相源在实例，--sync-skills 一键单向刷进模板（方案 C，开第二家公司时再换轨根层 junction）。整套规则固化在 PRINCIPLES P31，全组织一处真相。

OS · 并发控制

并发协作：工位卡、锁原语、原子取号

两个 AI 会话同时给同一份台账写「已占用」，谁后写谁覆盖谁——人肉眼看不见，数据悄悄坏。

痛点用户同时开了两个会话，都让 AI 从号池取号建工单。两个会话同时读到「TSK00011 未占用」，同时落笔——一个工单两个号，或两个工单一个号。数据库时代用事务解决；我们是纯文件，怎么办？
机制把操作系统文件并发的那一套搬过来：
  • 锁原语：file_lock（O_EXCL 创建锁文件 + 忙等超时 + 过期锁抢占）保护台账、建账等一切热写路径——只约束「同样走锁的写方」，机制层全员遵守
  • 原子写：atomic_write（唯一名临时文件 + os.replace）保证「写一半被读」不可能发生；临时文件掺 pid+纳秒，双写者不互踩
  • 写前日志（WAL）：取号协议 = 先占台账后建单，「写完并保存才算占到号」——先落日志再干活，崩溃了也不会开出幽灵工单
  • 原子取号：--new --auto-id 由生成器取「最大号+1」，目录存在性即锁，并发建单不撞号、自动登记台账
  • 工位卡：一个会话 = 一张卡（会话目录 + status），「台账写权 = 唯一在岗会话」；卡 3 天不动 = 僵尸工位卡，巡检自动收割（类比 waitpid）
落点巡检日志、巡检状态、worklog 追加全程持锁；服务端三个触发源（监听//sync/周期兜底）全程串行化。这些不是理论——「巡检日志重复追加」「tmp 互踩」「重复弹通知」都是真实踩过并在三轮体检中收口的坑。
09
OS · 微内核

OPC 服务：把散落的守护进程收敛成微内核

历史上这个系统靠「计划任务 + 双 watcher + 心跳脚本」维持运转——直到它们开始互相打架。

痛点v1 架构：登录自启脚本拉起两个 watcher（工单 + 看板各一个），再加计划任务心跳。问题接踵而至：watcher 和计划任务抢文件锁、谁先跑看运气；一台机器三套调度逻辑，出问题不知道查谁；新机器忘配置，看板悄悄变黄条。
机制决策 #18：全部收敛为一个常驻进程 opc_service.py——微内核化：
  • 进程 = 宿主，公司 = 租户：启动时扫描 opc.toml 装载全部公司，新公司自动纳管，互不串数据（多租户）
  • 内核服务：看板实时化（数据一变即重算 + 秒级监听）、巡检调度、实时通知与每日摘要、只读 API——全部进程内装配，配置驱动
  • 唯一调度权：旧的 watcher/计划任务全部退役，脚本降级为手动应急（默认一次性模式）——系统里只有一个会自己动的进程
  • 零感知运维：开机自启（Windows 启动文件夹 vbs / macOS·Linux crontab @reboot）、headless 无窗口、删文件即卸载、HTTP 探活感知端口顺延
落点微内核化的收益和操作系统教科书说的一模一样：调度逻辑唯一、故障域集中、新增服务（如将来的 agent 平台通知通道）按配置插拔，不碰内核。
10
Kubernetes · 控制循环

巡检 = 组织的 reconcile 循环

AI 员工会漏接单、忘推进、改了 A 忘了 B——靠经理每小时盯一眼？盯不住，也不该盯。

痛点传统管理是「人盯人」：例会、周报、口头催办。这套对 AI 组织失效——会话今天开明天关，没有「例会」可开。你需要一种不依赖任何人在场的管理方式。
机制不指挥每个动作，只声明「组织应该长什么样」（期望态），剩下的交给循环——Kubernetes 控制器模式：
① 期望态声明每单有主、无阻塞漏清、双账一致、号池有水、事务不脱期——13 项检查每项都是一条期望态
→
② 周期观测数据一变即巡检 + 周期兜底
扫文件真相，不猜、不忆
→
③ diff 偏差发现即结构化入待办
severity 三级：info / warn / critical 仅升级信箱
↺
④ 修正/告警处置置 handled 闭环
同一问题再犯自动 reopened

13 项期望态检查（选摘）

检查期望态被打破的样子
#1 解锁待开工前置工单已全部 done，本单还躺在 backlog——该开工了没人开
#2 认领缺口工单有 owner 但 worklog 无条目——接了单没记账，或根本没接
#3 双账对账task.md 与 worklog 说法不一致——以工单为准并告警
#4 脱期事务 / #11 逾期与停滞预警常设事务超期未推进；工单过了 due 或长期无更新
#5 升级信箱员工 [escalate] 请求总管决策——唯一 critical，必须打扰用户
#6 号池水位 / #9 僵尸工位卡 / #10 数据陈旧 / #13 依赖环号要耗尽、卡 3 天没动、看板数据过期、阻塞关系成环永久锁死
落点通知系统套用中断模型：severity = 中断优先级，quiet_hours 勿扰时段 = 中断屏蔽字（warn/info 夜间静默、并入次日 09:00 摘要，critical 永远直达）；通知只报「新出现」的偏差（哈希去重），不重复轰炸。巡检日志只增不删（审计流水），状态文件可改可重建（派生态）——主从分明。不在场模式（away_mode）= 中断总屏蔽：出差时实时通知全静默、每日摘要照常置顶未拍板项——绝不代决策。知识回流提示：升级/失败工单提醒总管把教训沉淀进知识库——教训有回家的路，二次踩坑即候选晋升为技能素材。

容错哲学 · P11

绝不静默：宁可标红，不可丢弃

系统对「错误数据」的态度，决定了一个组织能不能信任自己的看板。

痛点很多工具遇到脏数据直接丢弃：status 写错了？这条工单消失。日期格式不对？这条记录跳过。用户看到的是「少了一条」——他不知道是被删了还是本来没有，数据以静默的方式说谎。
机制OPC 的铁律（P11）：非法状态照常上板并标红，旁边配修法提示——数据绝不因格式错误而消失，修正后自动恢复正常渲染。全系统贯彻同一哲学：
  • 工单状态非法 → 上板标红 + 告警修法，不丢弃（P11）
  • 引用失效 → 门禁拦截 + 扫描自愈，绝不静默返回假路径（opc://org 多命中直接报歧义）
  • 巡检发现 → 只增不删的审计流水 + 可闭环的状态机，处置有痕、再犯重开
  • 服务后台循环异常 → 记入 last_error，/api/ping 可查，不做吞异常的「假健康」
  • agent 侧 [警告] 全部带修法话术——发现问题的同时告诉你怎么修
落点信任来自可预期：看板上的每一条你都敢信，因为「看不见」在 OPC 里不可能是「被藏起来」。
12
安全 · 最小权限

安全边界：读接口宽，写边界窄

本机服务也有安全模型——因为「任意网页都能摸到的本机端口」是真实攻击面。

痛点典型失误：本机 HTTP 服务把「重算数据」做成 GET 接口还没鉴权——任何网页里插一行 <img src="http://127.0.0.1:8765/api/x/sync">，你浏览恶意页面时它就在反复触发全公司重算与通知轰炸。静态文件服务的目录穿越（URL 编码反斜杠）则可能把公司根外的文件读出去。
机制读宽写窄（架构铁律）：
  • 只读 API：GET /api/{公司ID}/tickets、dashboard、patrol、ping 随便查——文件才是真相，读不改状态
  • 唯一写动作：POST /api/{公司ID}/sync（重算看板），同源校验（Origin 不匹配拒、Sec-Fetch-Site: same-site 也拒——本机另一端口同样算跨源），GET 直接 405
  • 双重防穿越：路径段按 / 与 \ 双分隔符切分过滤 + realpath 前缀校验，越界一律落回必然 404 的路径，绝不返回租户根目录列表
  • 失败可观测：后台循环异常记入 last_error 并暴露在 ping 里——「服务在跑」和「服务健康」是两回事
  • 写路径纪律：机制代码不写业务数据（文件是真相），只写自己的运行状态（巡检日志/状态/待办）
落点攻防两端都验证过：跨站 POST 实测 403、目录穿越实测 404、GET 退役实测 405——安全不是配置项声明，是 selftest 里的断言。

工程判断

边界：明确不做什么

一个系统的成熟度，看它拒绝了什么。

  • 不做细粒度权限系统：不给 agent 上目录级 user/group/permission 位。理由：AI 组织「越权」的代价低（git 可回滚）、灵活性的收益高，红线 + 锁 + 巡检已经覆盖真实风险——权限位是重机制，杀死灵活性。真实 OS 需要它是因为进程会失控，这里的「进程」是可对话纠正的 agent。
  • 不上私有数据库 / 不做服务端：文件即真相（02）的好处依赖这条底线。一旦状态进了数据库，「git 审计、双击即开、平台无关」全部作废。
  • 不过度设计遥测：技能命中率、token 成本统计已记账（等真实多公司跑起来有数据再做）——没有数据量的统计是伪需求。
  • 不用提示词解决机制问题：「请记得每次都检查 X」不是机制，是许愿。凡是必须发生的事，都下沉为门禁/巡检/selftest。
落点设计哲学一句话：能用机制的不用自觉，能用文件的不用服务，能借经典的不自创。
