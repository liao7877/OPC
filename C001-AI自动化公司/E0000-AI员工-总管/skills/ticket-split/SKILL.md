# 工单拆分 SOP（ticket-split）

> **输入**：已确认的需求（PRD 或父单正文）。**输出**：一组可直接分派的工单 + 父单闭环结构。

## 一、三条拆分原则（用户定稿）

1. **同一员工能完成的任务，尽量放一个工单**（一次派活一次交付，减少流转开销）；
2. **需要不同员工完成的需求，按员工边界拆成多个工单**（一单一 owner，铁律）；
3. **可并行的需求，即使同一员工也可拆多个工单**（配合并发机制：一个会话一个工单，多会话并行干）。

## 二、拆分自检清单（每个工单四项全过才准建单）

| # | 检查项 | 不过的处理 |
|---|---|---|
| 1 | **单一负责人**：一单只有一个 owner | 跨员工的活继续拆 |
| 2 | **独立可验收**：有明确验收标准和交付物，不用看别人干到哪才能判断 | 拆掉耦合部分，靠 inputs 引用上游产物 |
| 3 | **一会话粒度**：理想情况一个会话一口气干完 | 明显超大就继续拆 |
| 4 | **依赖显式化**：先后关系全部用字段声明（`inputs` + `blocked_by`），不许口头约定 | 补字段 |

## 三、建单流程

1. **建父单**（需求拆出 ≥2 个子单时）：`python ../../../../../opc_tickets.py --company C001 --new TSKxxx <需求名> --owner E0000`，然后手改 `type: 需求`，正文写 PRD 摘要 + 总验收标准 + 子单清单；
2. **建子单**：逐个 `--new`，frontmatter 补 `parent: <父单号>`；有前置的补 `blocked_by: [上游单号]`，需要上游产物的补 `inputs`；
3. **登记台账**：workbench/task-index.md 逐条登记（含父子关系列）；
4. **分派**：按 roster 选人（岗位匹配 + 负荷均衡），按 dispatch-sop 注入派发；
5. **父单跟踪**：子单全 done → 父单 review → 用户验收 → done。

## 四、依赖编排速查

| 关系 | 用法 |
|---|---|
| 下游开工前上游必须完成 | 下游 `blocked_by: [上游ID]` |
| 下游要用上游的产出物 | 下游 `inputs: [{name, path: tasks/<上游>/deliverables/…}]`（引用不复制） |
| 只是同一需求、无执行依赖 | 只挂 `parent`，不加 blocked_by（可并行就并行） |

## 五、红线

1. 不建"巨单"（一个单 N 个人干 N 件事）——宁可多拆；
2. 不建"碎单"（5 分钟的小活也建单）——直聊留痕即可，用户明确要追踪才建；
3. 子单没挂 parent、依赖没挂字段 = 拆分不完整，禁止分派；
4. 父单不承载具体执行（owner 恒为总管，只做验收闭环）。

## 六、不该开工单的活（边界判定，2026-08-28 决策 #17）

拆单前先问："这个活有终点吗？"

| 活的形态 | 正确去处 |
|---|---|
| 干一次就好 | 直聊记账（worklog type=直聊），不开工单 |
| 有终点、可验收 | 工单（本 SOP 拆分） |
| 多工单多角色、有交付终点 | 项目（P00xx） |
| **无终点、养资产、按节奏重复**（长期内容运营/文件维护/渠道经营） | **常设事务 AFF**——不是工单，不进本 SOP 拆分 |

事务建档：找总管分配 AFF 编号 → `workbench/affairs/AFFxxxx-标题/`（affair.md + assets/）→ 契约见 `opc://company:C001/workbench/affairs/AFF-SCHEMA.md`。事务的大活（改版/迁移等需验收的）照常开工单，worklog 条目带 aff 关联。
