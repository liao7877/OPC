# 总管记忆（MEMORY.md）

> 长期核心记忆：只记对下次干活有用的（决策、结论、坑）。
> 格式：五要素（场景/解法/适用前提/反例/验证）。

## 沉淀记录

### 2026-08-29 | 赋能/改造员工：先定信息架构，后动笔
- **场景**：用户提供整份角色蓝本（如《需求分析师×售前工程师 Skill》）要求"赋能给员工"。
- **解法**：动笔前先按**加载时机**给内容分诊——永远在场的素养/身份→员工 AGENTS.md；接单编排→workflow.md；按需查的知识/模板/话术→skill（触发词制，进 skills/ 并 sync-index）。源头文档是**原料不是产物**，按内容职能拆解落位，禁止整份倾倒成 SKILL.md 再返工。
- **适用前提**：目标体系有 AGENTS/workflow/skill 三层契约（公司模板 v2 均有）。
- **反例**：本次先把 297 行蓝本整份落成 SKILL.md，人设又写进 AGENTS.md，造成双真相源，用户指出后返工去重；且压缩时漏掉「持续进化」一条，去重前先补回才敢删。
- **验证**：改造完成后 grep 关键词，同一可加载内容在全公司只有一份副本；其余位置只允许存在指针。

### 2026-08-29 | 引用快照必漂移：清单只留指针
- **场景**：在 roster 备注、文档目录页、README 等处描述员工/技能/项目。
- **解法**：凡会变的事实清单（技能名/员工名单/目录名），一律写"见唯一权威（roster.md / skills/INDEX.md / team.md）"，不复制内容。
- **适用前提**：公司存在明确声明的唯一权威文件（目录结构说明书是总账）。
- **反例**：我在 roster 备注里复制了 E0001 的技能清单、在总管文档目录.html 里复制了花名册快照——次日实体一变即漂移；skills/README 的技能列表与 INDEX.md 生成物重复。
- **验证**：每次实体变更后 grep 旧快照字样应零命中（历史归档除外）。

### 2026-08-29 | 实体改名零改动（决策 #17 终版）：保留自解释目录名 + 一条命令
- **场景**：E0001 改名实战暴露全量手术问题；第一版方案（目录裸 ID 化）被用户否决——目录必须自解释。
- **解法**：目录名保留 `{前缀}{序号}-{名称}`（目录名为显示名真相，roster 岗位列须一致否则生成器告警）；引用层靠 ID 逻辑锚（前缀扫描）天然免疫改名；机械动作由 `opc_resolver --rename-entity E0001 新说明` 一条龙消化（git mv+链接+roster+看板+全文旧名改写），手动改名后跑 `--heal-entity-refs` 自愈，OPC 服务巡检周期兜底时也会重建断链（2026-08-29 决策 #18：原 30 分钟心跳已由常驻服务接管）。
- **适用前提**：散文写目录名没关系（改名后会被命令自动改写）；worklog/memory/archive 历史留痕区旧名只报不改（只增不删）。
- **反例**：删旧目录新建+逐文件搜替换（2026-08-29 E0001 改名实际发生的反模式）。
- **验证**：`opc_resolver.py --doctor` 全绿；散文引用零失效。

### 2026-08-29 | 总管行为准则：用户体验是唯一 KPI
- **场景**：一切汇报与施工决策。
- **解法**：公司只有一条主线——用户的一句话→信任的结果。①汇报只答"你现在需要知道什么/需要你决定什么"，施工过程进 messages.md；②机制类自营活的验收攒批轻确认，不逐单挂起；③机器故障（断链/陈旧数据）由 OPC 服务巡检与 doctor 先自愈，汇报里只留结论；④复杂度标尺=是否让主线更短更可信，答不出的机制提请精简。
- **适用前提**：用户是公司唯一用户，总管是产品负责人。
- **反例**：把 junction 断链、子节号撞车等车间事故推进用户视野；每个低风险动作都挂 review 等用户。
- **验证**：复盘每次对话：用户的等待步数与被卷入的内部细节是否减少。
