## 一、目标

在 `workbench/` 下交付一个**纯静态可视化协作看板**（单文件 HTML），数据源自 `workbench/tasks/` 各工单目录的 `task.md`。让廖哥与 AI 员工（E0000 总管 / E0001 分析员 / E0002 项目经理）能统一查看任务进度与详情，并支持搜索、筛选、按维度切换视图、以及查看工单在多人之间的**流转轨迹**。

## 三、数据模型（task.md 规范）

- **位置**：`workbench/tasks/TSKxxx-标题/task.md`
- **格式**：YAML frontmatter（代码块 `---` 包裹）+ 正文（描述）。目录名 `TSKxxx-标题` 同时携带 ID 与标题，frontmatter 为权威字段来源。
- **字段定义**：

| 字段 | 类型 | 取值 / 示例 | 必填 | 用途 |
|---|---|---|---|---|
| id | string | TSK00001 | 是 | 全局唯一编号 |
| title | string | 协作看板需求澄清 | 是 | 卡片标题 |
| status | enum | backlog / in_progress / review / done / failed / paused / cancelled | 是 | 看板分列依据 |
| owner | string | E0002 | 否 | 承接员工 ID（空则展示「未分配」） |
| owner_name | string | 项目经理 | 否 | 负责人可读名（**兜底字段**）：当 owner 代号在目录注册表中尚不存在（如先派活后建目录）时，看板以此名显示，使工单自包含 |
| project | string | P0001 | 否 | 所属项目 ID |
| project_name | string | 示例项目 | 否 | 项目可读名（**兜底字段**）：同 owner_name，用于目录尚未建立时的兜底显示 |
| priority | enum | 高 / 中 / 低 | 否 | 优先级圆点 + 筛选 |
| type | enum | 需求 / bug / 任务 | 否 | 类型筛选 |
| due | date | 2026-08-30 | 否 | 截止日展示 |
| tags | list | [前端, 工具链] | 否 | 标签筛选 |
| created | date | 2026-08-26 | 否 | 创建时间 |
| updated | date | 2026-08-26 | 否 | 更新时间 |
| completed_at | date | 2026-08-26 | 否 | **实际完成时间**：status=done 时填写（done 未填则生成器告警）；用于按期/逾期完成判断与统计 |
| handoffs | list | `[{from:E0001, to:E0002, at:2026-08-27, reason:需求澄清完成}]` | 否 | **流转链**：每次交接一条记录（F1）；空则无流转 |
| status_history | list | `[{to:in_progress, at:2026-08-26}]` | 否 | **状态变更时间线**：记录状态何时切换（审计补充，可选；详情页展示「状态轨迹」） |
| parent | string | TSK000 | 否 | **预留字段**（F2）：父工单 ID，未来子任务/拆解用，当前空着 |
| children | list | `[TSK00002, TSK00003]` | 否 | **预留字段**（F2）：子工单 ID 列表，未来用，当前空着 |
| links | list | `[TSK00010]` | 否 | **预留字段**（F2）：关联工单 ID 列表，未来用，当前空着 |
| inputs | list | `[{name:项目章程, path:opc://company:C001/project/P0001/project.md}]` | 否 | **输入物引用**：结构化引用工单开工所需的外部文件（相对 workbench/ 基准，不复制；可指向项目目录或上游工单 deliverables）；失效路径生成器告警 + 详情标 ⚠️ |
| description | text | 正文 | 否 | 详情描述 |

- **状态机**：`backlog → in_progress → review → done`；旁路 `failed` / `paused` / `cancelled`（取消——被否决/不需要做的工单置此，**不背「逾期」的锅**）。`status` 字段必填且必须取自上述枚举；缺失或非法时该工单**被生成器跳过并告警**（不会降级上板）。
- **逾期语义（completed_at 联动）**：「逾期中」仅对**活跃未完成**（backlog / in_progress / review）且 due 早于今天 0 点生效（卡片标红+「逾期」）；done（已完成）/ paused（有意暂停）/ failed（已定性失败）**不标逾期中**；done 且 `completed_at > due` → 「逾期完成」（卡片橙黄 + 详情显示逾期天数）；done 未填 `completed_at` → 生成器告警建议补填。
- **frontmatter 约定**：必须 `---` 包裹且单行 `key: value` 形式，禁止 YAML 多行/嵌套语法（生成器为轻量解析，不支持多行结构）。
- **代号→名称注册表（双来源、动态、非写死）**：看板显示的「员工名 / 项目名」由生成器在每次运行时动态构建，映射关系**不写死在代码里**：
  1. **来源一·目录扫描（权威）**：扫描公司根目录下 `E\d{4}-*` / `P\d{4}-*` 目录，取 `-` 之后部分（员工目录自动去掉 `AI员工-` 前缀）。**总管新建 `E0003-…` / `P0004-…` 目录后，下次生成自动收录，无需改任何代码。**
  2. **来源二·工单声明（兜底）**：若某工单 `owner`/`project` 引用了目录中尚不存在的代号（例如先派活、目录后建，或该实体无独立目录），则使用工单 `task.md` 里的 `owner_name` / `project_name` 兜底显示。**合并规则：目录优先；仅当目录查不到该代号时，才用工单声明的名称补全**——因此工单系统自身携带可读名称，不依赖外部目录存在与否。
- **输入物（inputs）机制**：工单开工前所需的外部材料（需求文档 / 上游交接物 / 参考资料）以**结构化引用**而非复制方式记录（保持单一真相、零漂移）：
  - 字段：`inputs` 列表，每项 `{name, path}`（path 为相对 `workbench/` 的路径；也支持纯路径字符串，name 自动取文件名）；
  - 可指向：项目目录（`opc://company:C001/project/P0001/…`）、上游工单交付物（`tasks/TSKxxx-…/deliverables/…`）、知识库等任意相对路径——**上一手的交付物天然是下一手的输入物**（与流转链闭环）；
  - 校验：生成器逐个检查路径存在性，失效告警但工单仍上板（不误伤）；看板详情「输入物」区块可点击跳转，失效项标红「⚠️ 路径失效」；卡片显示「📥 N 个输入」标记。
- **详情数据预生成（关键）**：因 `file://` 下 HTML 无法实时 fetch 本地文件，生成器须把以下数据**内联进 `tasks-data.json`**：
  - `messages.md` 全文
  - `deliverables/` 文件列表（文件名 + 相对路径）
  - `logs/` 文件列表（文件名 + 相对路径）
  - `handoffs` 数组（流转链，见 F1/F5）

## 五、看板功能需求

1. **主视图**：列 = 状态（待领 / 进行中 / 待审 / 完成 + 失败·暂停），卡片在列中流动。
2. **顶部工具栏**：
   - 分组维度切换：状态（默认）/ 项目 / 负责人 / **参与者（F5-②）**
   - 筛选条：优先级 / 类型 / 标签（多选）/ 搜索框（实时）
   - 主题切换：暗 / 亮（localStorage 记忆，默认暗）
3. **卡片**：标题 + **ID 标签（如 TSK00004）** + 状态色条 + 负责人（名称+代号小字）+ 优先级（**圆点+文字**：红=高 / 黄=中 / 灰=低）+ 项目标签 + 截止日（**逾期标红+「逾期」字样**）+ 流转标记（经手 N 人）+ 输入标记（📥 N 个输入）。
4. **详情面板**：点卡片弹出，展示 描述 + `messages.md` + `deliverables` 列表（可链）+ `logs` 列表。
5. **空状态**：`tasks/` 为空时各列显示占位提示。
6. **详情时间轴（F5-①）**：详情面板新增「流转轨迹」区块，按 `handoffs` 顺序展示 `谁 → 谁 / 时间 / 原因` 的链条（如 `E0001 分析员 —(08-27 需求澄清完成)→ E0002 项目经理`）。
7. **参与者分组维度（F5-②）**：顶部分组新增「参与者」；按工单历史经手人（当前 `owner` + `handoffs` 中所有 `from`/`to`）聚合，各经手人一列，工单只要在任一环节出现过即归该列——历史负责人也能在看板可见。
8. **卡片流转标记（F5-③）**：卡片显示「经手 N 人」标签，快速识别多经手工单。
9. **流转高亮（F5-④）**：最近（默认 7 天）发生过流转的工单卡片视觉突出（描边/角标），便于盯活跃单。
10. **顶部统计栏**：总数 / 各状态数量 / 逾期中 / 逾期完成（实时）。
11. **WIP 提示**：「进行中」列数量超上限（默认 6，常量可改）时列头标「⚠️WIP」。
12. **状态轨迹**：详情展示 `status_history`（状态变更时间线，审计补充）。
13. **描述 markdown 渲染**：链接/粗体/列表/行内代码（先转义防注入，危险协议链接拦截）。
14. **筛选持久化 + URL 分享**：筛选条件 localStorage 记忆；`?groupBy=&priority=&type=&search=` 参数直达视图。
15. **搜索防抖**：连续输入 150ms 防抖，大工单量下流畅。

## 六、使用方式

- 手动生成：`python generate_tasks.py`
- 自动监听：`python generate_tasks.py --watch`（后台运行，tasks/ 变动即重跑）
- 一键建单：`python generate_tasks.py --new TSKxxx 标题 [--owner E0001] [--project P0001]`（生成规范模板目录）
- 内置自测：`python generate_tasks.py --selftest`（9 项用例，全过退出码 0）
- 打开看板：双击 `kanban.html`（数据来自同目录 `tasks-data.js`；`file://` 下浏览器禁止 fetch 本地 JSON，故必须经 `.js` 入口）
- 自动同步：看板每 3 秒轮询重新加载 `tasks-data.js`，数据文件变动后**页面无感刷新**（方案 X）；亦可点右上角「🔄 同步」立即刷新
- 新增工单：按模板建 `TSKxxx-标题/task.md`，watcher 重跑后至多 3 秒内自动上板
- **工单流转（手工维护，F4）**：在 task.md 中把 `owner` 改为新负责人，并在 `handoffs` 数组追加一条 `{from:旧负责人, to:新负责人, at:今天, reason:交接原因}`；生成器重跑（或 watcher 自动重跑）后，时间轴 / 参与者分组 / 卡片标记 / 高亮即更新。看板本身**不写回**文件。

## 八、风险与约定

- **单一真相**：tasks/ 为唯一数据源；E0000 的 board.md / task-index.md 维持人工维护，不与看板自动同步（决策 7）。
- **解析容错**：
  - 缺 `---` 包裹（无 frontmatter）的 task.md 视为**坏文件，跳过并告警**，不上板；
  - `status` 非法或缺失的工单**跳过并告警**，不降级为 backlog（避免污染「待领」列）；
  - `owner` / `project` 等可选字段缺失则留空展示「未分配 / 未关联」，不跳过；
  - `handoffs` 中 `from`/`to` 若引用不存在的代号，看板回退显示代号（不报错）；`at`/`reason` 缺失则该条仅显示「未知时间 / 无原因」，不阻断渲染。
- **可移植**：kanban.html 依赖同目录 `tasks-data.js` 与 `tasks/` 下交付物相对路径，复制时整目录带走即可。
- **浏览器限制（file://）**：点击详情内交付物/日志链接为本地文件，部分浏览器对 `file://` 跨目录 `_blank` 打开会拦截；如遇拦截，用本地服务方式打开（`python -m http.server` 后访问 `http://localhost:8000/kanban.html`）即可正常跳转。

## 九、工单流转机制（详细）

### 9.1 为什么需要流转（而非拆工单）

工单协作有两种范式，二者是**分层互补**，不是替代：

- **流转（handoffs）**：同一工单、同一目标，人在换。适合「接力」——A 做完交给 B，还是同一张单。优点：上下文不丢、审计链清晰、看板按 owner 分组直观。
- **父子链接（parent / children / links）**：一个目标拆成多个独立子工单。适合「拆解/并行」——A 的活完成后新建 B 的子工单。优点：粒度小、责任清晰、天然支持并行。

真实企业系统（如 Jira）两者都有（assignee 变更历史 + Epic/Sub-task 层级）。对当前场景（AI 员工**接力式**工作），**以流转（A）为主最便宜、最贴合**；但数据契约中**预留 `parent`/`children`/`links` 字段**（F2），未来要拆子工单/关联时零成本扩展至 C。

### 9.2 数据模型示例

```yaml
owner: E0002
handoffs:
  - from: E0001
    to: E0002
    at: 2026-08-27
    reason: 需求澄清完成，转开发实现
  - from: E0002
    to: E0003
    at: 2026-08-29
    reason: 开发完成，转测试验收
# parent: 留空（未来用）
# children: 留空（未来用）
# links: 留空（未来用）
```

> ⚠️ 以上为**数据结构示意**。在 task.md frontmatter 中 `handoffs` / `inputs` **必须写成单行 JSON**（如 `handoffs: [{"from":"E0001","to":"E0002","at":"2026-08-27","reason":"…"}]`），生成器为极简单行解析，**不支持多行/嵌套 YAML**。

### 9.3 看板展示示例

- **详情时间轴**：`E0001 分析员 —(08-27 需求澄清完成)→ E0002 项目经理 —(08-29 开发完成)→ E0003 测试员`
- **参与者分组**：E0001 / E0002 / E0003 各一列，TSK00001 在三列都出现（历史负责人可见）
- **卡片**：「经手 3 人」标签 + 最近流转高亮描边

### 9.4 扩展到 C 的路径

预留 `parent`/`children`/`links` 字段已就位。未来加并行协作者（`collaborators` / `watchers`）+ 子任务拆解时，仅需：填字段 + 生成器解析 + 前端加对应视图（如「协作中」分组、子工单树），**不动数据模型根基**。
