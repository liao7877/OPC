> 范围：新建"经营驾驶舱 + 员工个人工作台 + 员工自记录机制"，与现有工单协作看板并存。
> 关联文档：`kanban.html` / `generate_tasks.py` / `tasks/`（现有工单体系，保留不动）

## 0. 背景与目标

- **现状**：已有工单协作看板（`kanban.html` + `generate_tasks.py` + `tasks/`），管理"公司派了什么工单"。
- **缺口**：
  1. 员工"自己干了什么"（尤其用户**直接对话**交代的小活、临时事）**没有落盘的真实数据源**。
  2. 缺少公司经营视角（人员、负荷、完成率、风险）。
  3. 缺少员工个人工作台（看不到自己计划/在做/做完，周报日报无据可查）。
- **目标**：建立 **员工自记录 → 个人工作台 → 公司统计** 的真实数据链路，看板只展示、数据全来自文件。

---

## 1. 核心原则

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | 看板只展示 | 所有看板只读文件，绝不直接写业务数据；写入只发生在员工维护自己的 `worklog.md`。 |
| P2 | 单一数据源 | 员工工作的真相 = 其 `worklog.md`；公司/个人看板均由此聚合，**禁止第二份手工维护的副本**。 |
| P3 | 真实文件来源 | 数据来自真实目录/文件（`worklog.md` + `roster.md`），看板如实反映，不造假不预填。 |
| P4 | 可扩展 | 看板模块做成插件式，新增模块不推翻主体。 |
| P5 | 复用不另起 | 沿用 `generate_tasks.py` 的"扫描 → 产出 `.js`（file:// 离线可读）→ HTML 读全局变量 → `--watch` 自动同步"套路。 |

## 2. 三块需求

### 2.1 公司级看板（经营驾驶舱）
参考工单看板，但**不是协作任务板**，是公司经营指标视图。模块（插件式，可扩展）：

1. **员工总览**：所有员工列表（岗位、在职/休假状态、点进去进他的个人工作台）。
2. **负荷与统计**：每员工 计划中/进行中/已完成 数量 + 公司汇总（总数、完成率、在岗人数）。
3. **近期动态流**：跨员工的工作记录时间线（谁、何时、干了啥），从各人工 `worklog.md` 聚合。
4. **逾期/风险**：进行中卡 >N 天未动、或超期未完的预警，让隐患浮出来。
- 另内链现有 `kanban.html` 作为"工单协作视图"入口。

### 2.2 员工个人工作台（点员工进入）
每个员工一个工作台视图，包含：

- **工作记录（必）**：`worklog` 按 计划中 / 进行中 / 已完成 三组展示。
- **我的统计卡片**：自身 计划中/进行中/已完成 数量 + 完成率，顶部小卡。
- **我的身份卡**：岗位、技能、在岗状态 + "回公司看板"入口。
- **交付物直链**：每条工作记录可挂 `deliverable` 文件，点开看交付物（报告/代码/文档）。

### 2.3 员工自记录机制
- 每位员工维护自己的 `worklog.md`（AI 员工 agent 操作自身目录下的文件）。
- **纪律（三段式）**：接到任何任务 → 建"计划中"条目；开始干 → 改"进行中"；干完 → 改"已完成"并挂 `deliverable`。
- 工单活与直聊小活都记，**统一来源**，周报日报直接从此出。

## 3. 数据模型：`worklog.md`

- **位置**：`E00x-岗位/workspace/worklog.md`（生成器递归扫描公司根 `E\d{3}-*/workspace/worklog.md`）。
- **格式**：多个 `---` 包裹的 frontmatter 块，每块一条记录（复用现有 `parse_frontmatter` 解析器，逐块解析）。
- **字段**：

| 字段 | 说明 | 必填 | 示例 |
|---|---|---|---|
| wid | 唯一ID（便于引用） | 否 | `W-20260827-01` |
| date | 创建日期 `YYYY-MM-DD` | 是 | `2026-08-27` |
| title | 事项 | 是 | `梳理公司看板需求` |
| status | **计划中 / 进行中 / 已完成** | 是 | `已完成` |
| type | 工单 / 直聊 / 自由（统计来源用） | 否 | `直聊` |
| deliverable | 产出文件路径（对应交付物直链） | 否 | `workspace/报告.md` |
| project | 关联项目 | 否 | `P0001` |
| updated | 最后更新时间 | 否 | `2026-08-27` |
| note | 备注 | 否 | `待复核` |

- **status 枚举**：`计划中` / `进行中` / `已完成`（独立于工单的 7 态状态机）。
- **示例**：
```
---
wid: W-20260827-01
date: 2026-08-27
title: 梳理公司看板需求
status: 已完成
type: 直聊
deliverable: workspace/公司看板需求.md
updated: 2026-08-27
---

---
wid: W-20260827-02
date: 2026-08-27
title: 搭建 dashboard 扫描器
status: 进行中
type: 工单
project: P0001
updated: 2026-08-27
---
```

## 5. 生成与同步（`generate_workbench.py`）

- 递归扫描公司根所有 `worklog.md` + 读 `roster.md` → 产出 `workbench-data.js`（含：员工注册表、各人工记录、公司聚合统计）。
- 支持 `--watch` 轮询 `worklog.md`/`roster.md` 变动自动重生成（沿用现有套路，≤3 秒同步）。
- **容错（沿用 `generate_tasks.py` 风格）**：
  - 坏条目（无 `---` 包裹 / 缺必填字段 / 非法 status）跳过 + 告警，不阻断整体生成。
  - 日期规整为 `YYYY-MM-DD`（补前导零，保证字典序 = 时间序）。
  - `deliverable` 路径失效告警（标 ⚠️，不阻断）。
- 离线友好：数据内联进 `.js` 全局变量（`window.WORKBENCH_DATA`），`dashboard.html` 用 `<script>` 引入，双击 `file://` 即可打开。

## 6. 看板设计（`dashboard.html`）

- **单应用双视图**：公司级（默认）+ 个人工作台（点员工进入），同一份数据两种呈现。
- **模块注册表（可扩展关键）**：每个模块 = 一个读 `WORKBENCH_DATA` 的渲染函数 + 一条导航项；新增模块只加"函数 + 导航"，不动现有模块代码。
- **个人工作台四组件**：工作记录分组 / 统计卡片 / 身份卡 / 交付物直链（见 2.2）。
- **数据加载**：`<script src="workbench-data.js"></script>` → 读 `window.WORKBENCH_DATA`。

---

## 7. 与现有体系关系

- `kanban.html` 管"工单协作"（数据源 `tasks/`）；`dashboard.html` 管"经营 + 个人"（数据源 `worklog.md` + `roster.md`）。
- 两套**数据源不同、互不冲突、不重复维护**；`dashboard` 内链 `kanban.html` 作为工单视图入口。
- 工单活已要求员工在 `worklog` 也记一笔（见 2.3），因此公司统计天然包含工单产出，无需从 `tasks/` 再拉一份。

## 9. 验收标准

1. 任意员工在 `worklog.md` 加一条记录并保存 → ≤3 秒后 `dashboard.html` 个人工作台与公司动态流出现该条。
2. 公司看板四模块数据均来自 `worklog.md` + `roster.md`，**无手工维护的副本**。
3. 新增一个看板模块只需加"渲染函数 + 导航项"，不改动现有模块代码。
4. 坏 `worklog` 条目不阻断整体生成，仅告警。
5. 员工接任务→计划中、开始→进行中、完成→已完成+交付物，三段式在自记录机制下可落地。
