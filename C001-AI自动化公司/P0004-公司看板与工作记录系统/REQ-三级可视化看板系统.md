## 二、背景与目标

- 已有工单体系回答"公司派了什么活"（`tasks/` + kanban.html），已在 P0004 立项并持续运行。
- 缺口：员工自主干的事（直聊小活、临时任务）无真实落盘数据源；缺公司经营视角（人员/负荷/完成率/风险）；缺团队维度的聚合视图；缺员工个人工作台。

## 四、数据模型

### 4.1 沿用 v1 并扩展：`worklog.md`（个人工作的唯一真相）

- 基础定义不变（位置 `E000x…/workspace/worklog.md`、`---` 多块 frontmatter、字段 wid/date/title/status/type/deliverable/project/updated/note、status 枚举=计划中/进行中/已完成）。详见 v1 §3。
- **v2 新增 `ticket` 字段**：`ticket: TSK00012`。规则：
  - `type: 工单` 的条目**必填** ticket；`type: 直聊/自由` 不可填；
  - ticket 引用不存在时生成器告警（⚠️ 不阻断）；
  - 该字段是 A2 决策的桥梁：个人台 W3 与 W4 中同一 TSK 互链，生成器将 worklog 工单型条目与 tasks-data.json 交叉核验。
- **家规「只增不删」（第三轮补充）**：worklog 条目一旦写入不允许删除或归档移走，只能推进 status/更新 updated——因为累计口径（§4.5）依赖完整历史，删条目会让历史统计倒退。归档机制留待未来按需立项。
- **起步方式（廖哥 2026-08-27 确认）**：不为员工预置 worklog 模板文件，三段式纪律与字段规范全部写在公司级 skill / 自记录机制（TSK00014）里。

### 4.2 新增：`project.md` 的 `team` 字段

- 格式：frontmatter 单行 `team: T001`；跨团队可写 `team: [T001, T002]`（生成器解析支持单值与数组）。
- 缺省语义：无 `team` 字段 = **公司直属项目**，只出现在公司级 M3，不进任何团队级 T3。（廖哥 2026-08-27 确认：项目不强制归属团队；存量 P0001~P0003 维持公司直属，**不补字段**。）
- 维护方：总管建项目时按需填写。

### 4.3 新增：团队公告文件（T5 数据源）

- 位置：`T001-AI开发团队/notices.md`（由总管/项目经理维护）。
- 命名说明：有意避开 `board.md`——E0000 下存在正在退役的老 `board.md`（工单看板遗物），同名不同物必生混淆。
- 格式：frontmatter 块式公告 `{title, date, author}` + 正文；具体字段随 TSK 实现细化，遵循"轻量解析、坏块跳过告警"的家规。

### 4.4 身份数据来源（注册表，A1/B2 拍板后定稿）

| 实体 | 权威来源 | 仲裁规则 |
|---|---|---|
| 员工清单 | 目录扫描（company 根 `E*` 目录存在即算员工候选，沿用"目录即真相"） | roster.md 未登记的目录 → 告警「未登记员工」；roster 登记但目录已删 → 该条忽略并告警 |
| 岗位 / 在岗状态 / 名称 | `E0000…/roster.md`（总管唯一维护点） | 文件系统推导不出这些属性，无仲裁问题 |
| **员工→团队归属** | **roster.md 团队列，唯一权威（A1 拍板）** | `team.md` 成员列表降级为说明文字并注明"以 roster.md 为准"；员工 AGENTS.md 不承载归属（功能单一不耦合）；roster 中引用了不存在的 tid → 告警 |
| 团队清单 | company 根 `T*` 目录扫描 + 各 `team.md` 信息 | — |
| 项目清单/归属 | company 根 `P*` 目录扫描 + 各 `project.md`（含 team 字段） | team 字段引用不存在 tid → 告警 |
| 代号→名称映射 | 沿用"目录扫描权威 + 工单声明兜底"双来源规则 | 与 generate_tasks 同构 |

### 4.5 统计口径（B1 拍板，M2/T2/W2 三处统一执行）

- **完成率 = 已完成 / 全部有效条目（累计口径，不看时间窗）**；分母不含已取消类条目。
- 「在途」= 计划中 + 进行中。
- 风险判定「N 天未动」默认 N=14，以 worklog 条目的 updated 字段为准；**阈值做成各页面顶部可调参数**（localStorage 记忆），缺省值集中一处配置、三页共享。

## 五、架构设计（`generate_dashboard.py`）

1. **单一生成器，一次扫描，分头产出**：递归扫描 company 根所有实体（roster / E*/worklog.md / T*/team.md+notices.md / P*/project.md）+ 复用工单产物 `tasks-data.json`（联动②③的数据来源，**不再重复解析 tasks/**，避免两套解析逻辑漂移；生成器检测 tasks-data.json 过期时告警提示先跑 generate_tasks.py）。
2. **产出的数据文件**：
   - `../../companies/C001/dashboard-data.js` → `window.DASHBOARD_DATA`（全量；dashboard.html 同在公司根）
   - `T001-AI开发团队/teamboard-data.js` → `window.TEAMBOARD_DATA`（该公司下所有团队的切片包，前端按参数取用；单团队目录固定取自身 tid）
   - 每个 `E000x…/mydesk-data.js` → `window.MYDESK_DATA`（单人数据 + 其工单切片；mydesk.html 在员工目录根）
3. **同步机制**：沿用 `--watch` 轮询 ≤3 秒重跑；页面轮询 data.js 自动刷新。**提供统一入口**（如一个脚本顺序拉起 generate_tasks 与 generate_dashboard 两个 watcher，避免两个常驻进程各自维护）。
4. **交叉核验（A2 拍板）**：worklog `type:工单` 条目与 tasks-data.json 逐条核对——①ticket 引用不存在 → ⚠️；②员工名下存在非终态工单但其 worklog 无对应进行中条目、或反之有"进行中"工单型条目但对应工单已 done/ cancelled → ⚠️ 提示双账不同步；核验只告警不阻断、不改数。
5. **容错家规**（沿用 generate_tasks.py 风格）：坏条目跳过+告警不阻断；日期规整 YYYY-MM-DD；deliverable/team/ticket 引用失效标 ⚠️ 不阻断；员工无 worklog 视为零负荷正常渲染。
6. **离线友好**：全部数据内联 .js 全局变量，`file://` 双击即开，各层页面相对路径互链（dashboard → mydesk → dashboard 双向跳转均为相对路径）。

联动②③的"点击看详情"依赖 kanban.html 的深链能力，当前不存在，需**先行交付一张前置小工单**：

### 数据新鲜度与保活（第三轮拍板：防"静默死数据"）

**前提认知**：`file://` 下浏览器无法执行本地脚本，「🔄 同步」按钮与每3秒轮询只能**重拉数据文件**（沿用工单看板现成机制：动态重插 data.js + `#_=时间戳` cache-buster），**真正的重新生成必须由 HTML 之外的力量完成**。因此保活是三层防线：

| 层 | 机制 | 说明 |
|---|---|---|
| ① 页面内（防欺骗） | 沿用同步按钮+3秒轮询+「数据生成于 generated_at」展示；**新增陈旧告警**：当前时间 - generated_at > 可配阈值（默认10分钟，与§4.5 同款 localStorage 记忆）→ 状态条变黄提示「⚠️ 数据已陈旧 N 分钟，生成器可能未运行」；data.js 加载失败 → 明确报错并提示运行命令（沿用工单看板 onerror 文案风格） | 保证用户永远不会把旧数字当新数字 |
| ② 计划任务（自愈） | Windows 任务计划程序开机自启**统一入口脚本**：顺序拉起 generate_tasks 与 generate_dashboard 两个 watcher → 使用者零感知 | 建议 TSK00020 承接（含入口脚本与注册说明） |
| ③ 会话 SOP（兜底） | 总管开工 SOP 中加一步：先跑一次两个生成器再干活（AI 公司场景下最自然的兜底）；写入 dispatch-sop 或总管 skill | 保证不开计划任务时也能随手刷新 |

### 第三轮补充约定

- **扫描范围收紧（A4 拍板）**：参与本看板体系的员工目录**必须位于公司根目录下**（`E*/workspace/worklog.md` 扫描约定不变）；员工目录外置不在本期支持范围。「位置无关」原则在本体系内降级为"逻辑归属无嵌套关系，物理上收在公司根内"；roster 中出现根外路径 → 告警。**待办提醒**：company.md「员工位置无关」原则行建议随后微调措辞以消除歧义（涉及组织级文档，另行走文档维护流程）。
- **透明度假设**：公司级动态流等模块向查看者展示全员工作记录，无权限体系——基于"本机单人查看"的前提，作为明确设计假设记录。
- **W4 在途定义细化**：paused 工单**显示但置灰**，不计入「在途」统计口径。

## 七、验收标准（增量部分）

1. 打开三个层级的 HTML，双击 file:// 各自独立可用，互链跳转正确。
2. 给任一 project.md 写入 `team: T001` 并重跑生成器 → 该项目出现在团队级 T3 且公司级 M3 显示团队徽标。
3. 在任一成员 worklog 加一条记录 → ≤3 秒后公司动态流（M5）、团队动态流（T4）、其个人台（W3）同时出现。
4. 员工名下有在途工单时，其 mydesk W4 能列出并可跳转 kanban 详情；工单流转后同步变化。
5. 无 team 字段的项目不出现在任何团队级看板，仅在公司级显示。
6. 停掉生成器超过陈旧阈值后刷新页面 → 状态条变黄并提示"数据已陈旧"；重新运行生成器 → 提示消失、数据恢复 ≤3 秒同步（保活第①层验收）。
7. 员工目录若被移出公司根 → roster 扫描告警「员工目录不在公司根下」，看板统计给出明确缺失提示而非静默少人（A4 收紧约定的守门验证）。
