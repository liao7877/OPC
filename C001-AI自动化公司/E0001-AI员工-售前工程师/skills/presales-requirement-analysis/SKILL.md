# 需求分析师 × 售前工程师复合技能（presales-requirement-analysis）

> 用途：E0001 执行需求分析、方案设计、售前文档、客户沟通类任务的方法论主干与质量铁律。
> 每次输出都应达到「可直接提交给客户/高管/开发团队」的专业水准。
> **素养基线不在本技能**：职业素养（思维/行为/沟通层）的唯一权威在员工 AGENTS.md「素养基线」节（每会话必载，勿在此重复）。
> **素材按需读**：文档模板与话术提纲 → [templates.md](templates.md)；能力矩阵/知识储备/书单 → [capability-matrix.md](capability-matrix.md)；交稿前完整自检清单 → [checklists.md](checklists.md)。

## 一、两套工作法（选对再动手）

**需求分析五步法**（做需求时）：
1. 需求定义（Why）→ 需求背景说明书
2. 需求捕获（What）→ 原始需求清单、调研报告
3. 需求分析与建模（How）→ 优先级矩阵、流程图、用例图
4. 需求规约（Document）→ BRD/MRD/PRD/SRS 正式文档
5. 需求验证与跟踪（Validate）→ 评审纪要、RTM、变更记录

**售前方案六步法**（做方案时）：
1. 客户画像与需求洞察 → 客户画像、需求洞察报告
2. 现状与差距分析 → 差距分析报告
3. 方案架构设计 → 架构设计图、方案蓝图
4. 价值量化与 ROI 论证 → ROI 分析报告
5. 落地路径规划 → 实施路线图、项目计划
6. 风险与保障 → 风险评估表、服务保障方案

## 二、文档选型（写哪一种别选错）

| 类型 | 核心目的 | 阅读对象 |
|---|---|---|
| BRD | 论证商业可行性，争取资源 | 高管、决策者 |
| MRD | 定义市场需求与产品方向 | 产品总监、市场 |
| PRD | 定义产品功能与实现细节 | 设计、开发、测试 |
| SRS | 定义软件系统需求规格 | 开发、测试、架构 |

## 三、需求描述五条铁律（每条需求必过）

1. **完整性**：谁（Who）在什么场景（When/Where）做什么（What），达到什么目的（Why），如何验证（How）。
2. **可测试性**：有明确验收标准，禁用模糊词（"快速""友好""大量"）。
3. **一致性**：术语统一、逻辑自洽、前后呼应。
4. **可追溯性**：唯一编号，可追溯到业务目标、设计文档、测试用例。
5. **优先级明确**：MoSCoW 标注（Must/Should/Could/Won't have）。

## 四、输出质量门槛（交稿前必过）

- 需求类：编号与优先级齐全；术语有定义；流程覆盖正常/异常/边界；每条有验收标准；非功能需求（性能/安全/兼容）明确；干系人已确认。
- 方案类：痛点有数据支撑；架构可行性已验证；ROI 可计算；里程碑明确；风险有应对；竞品对比客观。
- 完整清单（交重要稿件前逐项过）→ [checklists.md](checklists.md)。

## 五、表达纪律

- 沟通话术、访谈提纲、会议议程不临场发挥——从 [templates.md](templates.md) 取对应框架，按客户情况填空。
- 量化优先：能写数字不写形容词（节约 X 元/人日、提升 X%）。
- 知识盲区先查 [capability-matrix.md](capability-matrix.md) 的知识储备与书单补课，再动笔。
