# 需求分析师 × 售前工程师复合技能（presales-requirement-analysis）

> 用途：E0001 售前工程师执行需求分析、方案设计、售前文档、客户沟通类任务时的方法论与规范唯一来源。
> 级别：E0001 私有技能（2026-08-29 由用户提供的能力蓝本落地）。
> 使用准则：当接到任何与需求分析、方案设计、文档撰写、客户沟通相关的任务时，始终以本技能定义的能力矩阵、方法论和文档规范为准，输出专业、严谨、可直接落地执行的内容；每一次输出都应达到「可直接提交给客户/高管/开发团队」的专业水准。
> **素养基线不在本技能**：职业素养（思维/行为/沟通层）的唯一权威在员工 AGENTS.md「素养基线」节（每会话必载，勿在此重复）。

| **需求管理** | 掌握需求变更控制、需求跟踪矩阵（RTM）、需求评审与确认流程 | 变更申请单、RTM、评审纪要 |

## 二、工作方法论（Methodology）

### 2.1 需求分析五步法
```
Step 1: 需求定义（Why）
  → 明确业务背景、痛点、目标用户、成功指标
  → 输出：需求背景说明书

Step 2: 需求捕获（What）
  → 通过访谈/问卷/观察/竞品分析收集原始需求
  → 输出：原始需求清单、用户调研报告

Step 3: 需求分析与建模（How）
  → 分类整理、去伪存真、优先级排序、流程建模
  → 输出：需求优先级矩阵、业务流程图、用例图

Step 4: 需求规约（Document）
  → 编写标准化需求文档（BRD/MRD/PRD/SRS）
  → 输出：正式需求文档

Step 5: 需求验证与跟踪（Validate & Track）
  → 需求评审、原型确认、测试用例评审、变更管理
  → 输出：评审纪要、RTM、变更记录
```

### 2.2 售前方案设计六步法
```
Step 1: 客户画像与需求洞察
  → 了解客户行业、业务现状、痛点、决策链、预算
  → 输出：客户画像、需求洞察报告

Step 2: 现状与差距分析
  → 分析客户现有系统/流程与目标状态的差距
  → 输出：差距分析报告

Step 3: 方案架构设计
  → 设计整体技术架构、功能架构、数据架构
  → 输出：架构设计图、方案蓝图

Step 4: 价值量化与ROI论证
  → 量化方案带来的效率提升、成本节约、收入增长
  → 输出：ROI分析报告

Step 5: 落地路径规划
  → 制定分阶段实施计划、里程碑、资源投入
  → 输出：实施路线图、项目计划

Step 6: 风险与保障
  → 识别技术/业务/组织风险，给出应对措施与保障承诺
  → 输出：风险评估表、服务保障方案
```

## 三、需求文档撰写规范（Document Standards）

### 3.1 文档体系

| 文档类型 | 全称 | 核心目的 | 阅读对象 | 关键内容 |
|---------|------|---------|---------|---------|
| **BRD** | Business Requirement Document | 论证商业可行性，争取资源 | 高管、决策者 | 商业目标、市场机会、盈利模式、成本收益、风险评估 |
| **MRD** | Market Requirement Document | 定义市场需求与产品方向 | 产品总监、市场 | 市场分析、用户画像、竞品分析、功能规划 |
| **PRD** | Product Requirement Document | 定义产品功能与实现细节 | 设计、开发、测试 | 功能描述、业务流程、交互逻辑、数据埋点、验收标准 |
| **SRS** | Software Requirement Specification | 定义软件系统需求规格 | 开发、测试、架构 | 功能需求、非功能需求、接口定义、数据字典 |

### 3.2 PRD文档标准模板（大厂规范）

```markdown
# PRD文档：[产品/功能名称]

## 1. 文档概述
### 1.1 修订记录
| 版本 | 时间 | 修订人 | 修订内容 | 备注 |

### 1.2 项目背景
- 现状描述 + 影响范围 + 期望效果

### 1.3 需求目标
- 明确可量化的成功指标（如：转化率提升X%、操作步骤减少Y步）

### 1.4 阅读对象
- 产品、设计、开发、测试、项目经理、业务方

### 1.5 专业术语
- 列出文档中涉及的专业名词及解释

## 2. 项目概述
### 2.1 产品路线图
### 2.2 功能清单（Feature List）
### 2.3 产品结构设计
### 2.4 业务流程图（泳道图/活动图）
### 2.5 需求列表（Backlog）

## 3. 产品规范
### 3.1 页面设计规范
### 3.2 产品状态规范
### 3.3 操作提示规范
### 3.4 数据加载规范
### 3.5 消息通知规范

## 4. 功能需求（核心章节）
### 4.1 功能总览
### 4.2 页面原型（含交互说明）
### 4.3 用例描述（Use Case）
  - 用例名称、参与者、前置条件、后置条件、主流程、异常流程
### 4.4 业务规则
  - 校验规则、计算逻辑、权限规则、状态流转规则

## 5. 非功能需求
### 5.1 性能需求（响应时间、并发量、吞吐量）
### 5.2 安全需求（数据加密、权限控制、等保合规）
### 5.3 兼容性需求（浏览器、设备、系统版本）
### 5.4 可用性需求（无障碍、国际化）

## 6. 数据需求
### 6.1 数据埋点清单
### 6.2 数据指标定义
### 6.3 数据报表需求

## 7. 附录
### 7.1 接口需求（如有）
### 7.2 附件素材（设计稿、参考文档）
### 7.3 风险与依赖
```

### 3.3 需求描述黄金法则
1. **完整性**：每个需求必须包含"谁（Who）在什么场景（When/Where）做什么（What），达到什么目的（Why），如何验证（How）"。
2. **可测试性**：每个需求必须有明确的验收标准，避免模糊词汇（如"快速""友好""大量"）。
3. **一致性**：术语统一、逻辑自洽、前后呼应。
4. **可追溯性**：每个需求有唯一编号，能追溯到业务目标、设计文档、测试用例。
5. **优先级明确**：使用MoSCoW法则标注 Must have / Should have / Could have / Won't have。

## 四、沟通与表达模板（Communication Templates）

### 4.1 客户需求访谈提纲
```
1. 【背景】贵司目前的[业务领域]整体运作流程是怎样的？
2. 【痛点】在日常工作中，最让您头疼的3个问题是什么？
3. 【影响】这些问题对业务/团队/客户造成了什么具体影响？（量化）
4. 【期望】如果有一套理想的解决方案，您希望它帮您实现什么？
5. 【约束】在推进这个项目时，有哪些必须考虑的约束条件？（预算、时间、技术、合规）
6. 【决策】这个项目的决策流程是怎样的？关键决策人有哪些？
7. 【竞品】您目前是否了解或使用过类似的解决方案？体验如何？
```

### 4.2 方案价值呈现话术框架
```
【痛点共鸣】"根据我们的调研，贵司目前在[具体场景]面临[具体痛点]..."
【方案概述】"我们的解决方案通过[核心技术/方法]，帮助您[实现目标]..."
【价值量化】"预计上线后，可实现[具体指标提升]，每年节约[金额]/提升[效率]..."
【落地保障】"整个实施周期预计[X个月]，分[X个阶段]推进，我们有[X个同行业成功案例]..."
【风险兜底】"针对您担心的[具体风险]，我们的应对措施是[具体方案]..."
```

### 4.3 需求评审会议议程
```
1. 需求背景与目标回顾（5分钟）
2. 业务流程与功能演示（15分钟）
3. 技术可行性讨论（15分钟）
4. 风险与依赖识别（10分钟）
5. 排期与资源确认（10分钟）
6. 待办事项与责任人明确（5分钟）
```
