Multica 开源项目调研报告

OPC 组织级情报 · 调研日期 2026-08-29 · 数据源：GitHub API 实时拉取 + 官方仓库原始文件 + 第三方实测
一句话结论：Multica 不是"一人公司"项目，它是一个"人机混合团队的项目管理平台"——本质是给 Jira/Linear 装上 Agent 执行层。

网上"一人公司神器"的说法是媒体二次包装，官方 VISION.md 只字未提"one-person company"。真正在做"AI 公司"这个形态的是 Paperclip（79,555 stars，MIT 协议），比 Multica 还火。如果你的目标是"一人 + 一群 Agent 跑公司"，Paperclip 是更对味的参照物；如果你的目标是"把我已有的多个 Agent CLI 管起来、任务能追踪、经验能沉淀"，Multica 才合适。

1. 定位纠偏：它到底是什么

这是本次调研最重要的一个发现。廖哥问的是"搭建一人公司的一个项目"，但 Multica 官方对自己的定义完全不同。

官方一句话"Make humans and AI agents work as one team — open-source and self-hostable."（GitHub 仓库描述）
官方 VISION"成为人机协同工作的 system of record and action"。核心比喻是 1960 年代的 Multics 分时操作系统——把算力分给多人。文档通篇讲 team、teammate、assignee、review，没有一处提到 one-person company 或 solo founder。
媒体包装"你的下一批 10 个新员工不会是人类"、"一人公司神器"、"OPC 触手可及"——这是中文科技号和 SEO 作者为了流量做的二次解读。
准确类比"Linear / Jira 的 Agent 化版本"。第三方评测的原话最准："a Jira board where some assignees happen to be bots"（一个碰巧有些执行者是机器人的 Jira 看板）。
为什么这个区分很重要

定位决定了产品形态。Multica 的核心抽象是 Issue（工单）——一切围绕"谁被分配了哪张卡"。而"一人公司"需要的核心抽象是 组织（岗位、汇报线、预算、目标拆解）。这两个抽象不通用：你能把任务派给一个 Agent，但没法在 Multica 里定义"CTO 向 CEO 汇报、月度预算 50 美元、超支自动停"。

后者正是 Paperclip 在做的事（见第 7 节）。

3. 架构与核心能力

3.1 三层架构

        Web  ·  Desktop (macOS/Windows/Linux)  ·  iOS
                          │
                          ▼
   ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐
   │   Next.js    │──>│  Go backend  │──>│   PostgreSQL     │
   │   frontend   │<──│  (Chi + WS)  │<──│   (17)           │
   └──────────────┘   └──────┬───────┘   └──────────────────┘
                             │  tasks over WebSocket
                      ┌──────┴───────┐
                      │ Agent daemon │  跑在你机器上，紧挨着你的代码
                      └──────┬───────┘
                             │  spawns
                      ┌──────┴───────────────────────────────┐
                      │  Claude Code · Codex · Cursor · …    │
                      │  （共 23 个 runtime）                │
                      └──────────────────────────────────────┘

关键设计：Multica 不自带模型，也不实现 Agent 循环。它只是 shell out 到你已经装好、已登录的 CLI。这个取舍很聪明——Agent 生态变化太快，它只想做那个"不管谁赢都能活下来的层"。

3.2 支持的 23 个 Agent CLI

对廖哥的直接利好

官方 runtime 列表里包含 codebuddy（CodeBuddy）。也就是说你现在主力用的 WorkBuddy/CodeBuddy 可以直接被 Multica 纳管，不需要换工具链。

完整列表 Claude Code、OpenAI Codex、Cursor Agent、GitHub Copilot CLI、OpenCode、OpenClaw、Hermes、Pi、Antigravity、CodeBuddy、DevEco Code、Grok、Kimi、Kiro CLI、Qoder CLI、Qoder CN、Qwen Code、QwenPaw、Reasonix、Trae CLI、DeepSeek Harness、Oh-My-Pi、MiniMax Code、Dim
接入方式daemon 扫描 PATH 自动发现，装了哪个 CLI 就用哪个。切换 provider 是下拉框，不是迁移。

3.3 五大核心能力

Agent 即队友Agent 有档案、头像，出现在看板上、评论区发进度、主动报 blocker。Issue 可以像派给同事一样派给它。
Squads（小队）把多个 Agent 和人归到一个 leader 下面，任务派给小队而不是个人，由 leader 决定谁接。抽象成 @FrontendTeam 而不是 @张三。
Autopilotscron / webhook / 手动触发的周期性任务。每日站会、周报、定期审计可以全自动跑起来。这个能力最接近"无人值守公司"。
Skills 复用宣称"每个解决方案都沉淀为全队可复用技能"。但注意：实测这个能力目前大半是营销话术，见第 5 节。
执行可观测完整的执行日志（每次工具调用、命令、错误，带时间戳）、token 用量按 agent/issue 统计、失败自动重试或停下报原因、Review gates（产出先进 review 不进 main）。

3.4 部署形态

云端multica.ai 注册即用，零配置
桌面端Electron，macOS / Windows / Linux。跑在哪台机器上，就把那台机器自动注册成 runtime
自托管Docker Compose 或 Helm chart（k8s）。官方实测 idle 内存约 100MB（web 50MB + backend 7MB + PG 42MB）——服务端非常轻，吃掉资源的是 Agent 本身
最低配置服务端：2 vCPU / 2GB RAM 跑得动。想在同一台机器上并行跑 Agent，上到 4 vCPU / 8GB

4. 许可证红线（自部署前必读）

这不是 Apache 2.0

我拉了官方 LICENSE 原文（328 行）逐条核对。它是 Apache License 2.0 完整全文 + Part I 附加条件的组合体，附加条件优先于 Apache 正文（Part I 第 3.c 条明确："If Part I and Part II conflict, Part I controls"）。GitHub 因此无法识别为 SPDX 标准协议，标记为 NOASSERTION。

4.1 四条关键限制

① 禁止对外托管 未经商业授权，不得用 Multica 源码向第三方提供托管服务，也不得把它作为组件嵌入对外销售/分发的产品。
  • 即使免费、无广告、无付费档，只要是给外部用户访问的公开实例，仍需商业许可
  • 单一组织内部使用（含多工作区）不需要商业许可——这条对廖哥自用是放行的
  • 发布 fork 源码到公开仓库不算托管服务，允许，但接收方要运营托管仍需各自拿许可
② 不许拆品牌 未经书面的 branding waiver，不得移除或修改 Multica 的 LOGO、产品名、UI 中的版权与署名信息。
  • 覆盖 apps/web/、apps/desktop/、apps/mobile/、packages/views/、packages/ui/，以及 Docker 镜像 ghcr.io/multica-ai/multica-web
  • 且明确写着：改了、搬了、重命名了、抽到别的包里，照样受约束
  • 豁免场景：只用后端 server/、daemon 或 CLI，不分发也不运行 Multica 的 UI
③ 非 UI 使用要署名如果只用后端/daemon/CLI 做产品，必须保留所有版权专利商标声明，并在用户可见文档中声明"built on Multica"并附 GitHub 链接。
④ 贡献者条款提交 PR 即视为同意：官方可以随时把协议改严或改松，且你的代码可被用于其商业云业务。

4.2 对 OPC 场景的判定

自用（一人 + 自己的 Agent 团队）✅ 完全允许，无需商业许可
改 UI / 换品牌名后自用⚠️ 条款上不允许（第②条），除非拿到书面 branding waiver
做成产品对外卖 / 给客户部署❌ 需要商业许可，否则违约
只借鉴架构思路，自己实现✅ 思路不受版权保护，可放心借鉴
与 OPC 现有机制的冲突点

廖哥的 OPC 有一套自建的品牌与治理体系（公司命名空间、员工卡、总管 E0000）。如果哪天想让 OPC 跑在 Multica 之上并对外提供服务，第①条是直接红线；如果只是自用且保留 Multica 品牌，则没障碍。

另外④值得警惕：给 Multica 贡献代码等于授权它单方面改协议，这在开源项目里属于相当强势的条款。

5. 真实坑与成熟度评估

这一节全部来自第三方实测博客和仓库自身 issue，不是媒体通稿。诚实说：这是个高速迭代的 v0.4.x，不是成品。

5.1 已确认的真实问题

编排名不副实 最硬伤的一条。实测者配置了一个"自动派单的编排 Agent"，反复报 multica cli is not authenticated。根因：被 spawn 出来的子 Agent 进程不继承父进程的认证上下文。结果是——号称自动编排，实际上任务仍得手动分配给 Agent。
来源：tim.bai.uno 实机测试 实测
凭证传递断裂 从 GitHub clone 的仓库里，Agent 拿不到 .env 里的 API key（spawn 的进程访问不到）。需要人工介入配置。
同上 实测
Skills 不会自动沉淀 宣传语是"每个解决方案都自动变成可复用技能"，但自动蒸馏管线仍在开发中。今天的 skills 基本是手写 runbook。想要复利，得靠自己写。
来源：andrew.ooo 深度评测 实测
无 per-agent 预算上限 每个 CLI 各走各的账单，Multica 没有"这个 agent 花了 42 美元"的硬性熔断。成本控制得自己去 provider 后台做。这一点 Paperclip 有而 Multica 没有。
Kanban 里 Agent 失败很难看人从"进行中"挪到"阻塞"只挪一次；Agent 卡在循环里，90 秒能刷五次状态迁移，把看板淹掉。
自托管登录有坑 默认鉴权走云端发验证码，全自托管且没接云端时，验证码永远收不到，卡在六位输入框。变通方法：设 APP_ENV=development + 清空 RECENT_API_KEY，此时任意六位码可登录，首个账号即管理员。但这不是生产级鉴权模式，别直接暴露公网。
来源：mejba.me Hetzner 部署实录 实测
云版与自托管不同步新功能先上 Cloud，自托管 GHCR 镜像有时滞后一个版本。自托管需要盯 release notes。
安全项仍在补2026-04-25 单日收到 6 个安全/API 审计级 issue：429 缺 Retry-After、/auth/verify-code 无暴力破解防护、状态变更请求未校验 Origin、PATCH /api/comments/:id 返回 404（只有 PUT 能用）。属于 P0/P1 级发现。

5.2 仓库自身的开放式争议

"I think Multica is impressive work… But the underlying mental model is still 'a Jira board where some assignees happen to be bots.' Agents have radically different failure modes than humans."

—— 仓库 issue #815 原文，标题《Multica still manages AI the way it manages people》官方仓库

这条来自仓库自身、15 条评论的讨论，指向一个未解的产品问题：用人类的项目管理抽象管 Agent，在 100 个 Agent 的规模下还成不成立？Agent 可能需要的是心跳、预算、审批门这类原生原语，而不是看板列。

其他高热反馈还包括：

  • #1943 [Feature] Workflow Orchestration（16 评）—— 编排能力仍被强烈呼唤
  • #1014 [Feature] OIDC 登录（15 评）—— 企业身份集成缺失
  • #4490 [Feature] 插件/扩展系统（10 评）—— 目前没有扩展机制
  • #1211 讨论：团队知识是否该像 skills 一样跨 run 沉淀（14 评）—— 说明还没做到
  • #3262 [Bug] Codex app-server 卡在 running 无输出；#2341 [Bug] 只有 1 个任务时 Agent 卡在 Queue；#4601 [Bug] 团队长叫不醒成员

5.3 成熟度判定

适合谁 已在跑 2 个以上 Agent CLI、受够了 tmux 的 2–10 人团队；想要统一看板 + 供应商中立 + 自托管的团队；想用两个模型家族做并行 code review 的场景。
不适合谁 只跑单个 Agent 的独狼（UI 开销收不回本）；今天就需要重型治理、审批链、per-agent 预算上限的团队；不想运维 PostgreSQL 的人；需要稳定 v1 API 契约或已过外部安全审计的团队。
总体早期生产可用（early production for low-risk projects）——第三方评测原话。真实工程，但不是成品。

6. 与 OPC 体系的关系

核心判断：不在同一层，是互补而非替代

廖哥的 OPC（E:\OPC）是治理规范层——命名空间 opc://、公司/员工卡、总管 E0000、看板生成器、pre-commit 门禁。它的立身之本是"散落路径收敛到配置、改名只改一处、文档层符号化"。

Multica 是执行平台层——它需要 PostgreSQL + Docker + daemon，把 Issue 派给 CLI 去跑。

两者解决的是不同问题：OPC 解决"组织知识怎么组织、引用怎么不失效"；Multica 解决"Agent 活儿怎么派、进度怎么看"。

6.1 三个值得借鉴的设计

① Runtime 抽象 Multica 不绑任何 Agent CLI，vendor 中立——"切换 provider 是下拉框，不是迁移"。这跟 OPC 的"稳定锚"思路异曲同工：易变的物理布局下沉到一层间接。OPC 已在公司目录改名这件事上做到了，Multica 把它做到了 Agent 选型上。
② Autopilots cron/webhook 触发周期性工作（每日站会、周报、定期审计），每个 autopilot 自动建 Issue 并路由给 Agent。这个机制和 OPC 的 opc_patrol.py 巡检是同一类东西，可以对照看 Multica 怎么把"巡检→发现→派单→回报"串成闭环。
③ Review gates 产出进 review 不进 main，"没有人类点头不许上线"。OPC 目前靠 pre-commit 门禁做静态校验，Agent 产出的人工审批环节还比较薄。

6.2 不建议照搬的部分

  • 不要为了 Multica 把 OPC 迁到数据库上。OPC 的文件系统 + 文档驱动是其最大优势：可读、可 diff、可 git 版本管理、零运维。Multica 的 PostgreSQL 依赖是它自己的负担（第三方评测明确列为 adoption 门槛）。
  • 不要接受"每个解决方案自动沉淀成技能"的说法。这能力 Multica 自己都没做出来，OPC 里若要沉淀经验，还是得靠人工写进 memory/技能文件。
  • 警惕协议传染。如果将来 OPC 想产品化对外，Multica 的第①条红线会挡路。借鉴思路零风险，直接依赖有风险。

8. 资料可信度警告

中文资料大量是 AI 洗稿，与官方文件直接矛盾

调研过程中撞上两篇技术细节完全错误的中文文章，如果照着做会白折腾：

  • 某 CSDN 文章称 Multica 用 Rust 写协调内核、FastAPI 做网关、四层 Docker 服务。全部是幻觉——官方架构图明确是 Go 后端 + Next.js 前端 + PostgreSQL，没有 Rust，没有 FastAPI，没有"Coordinator Core"这个概念。
  • 某部署教程称自部署"必须启用 Kubernetes""内存不低于 6GB"。与官方 SELF_HOSTING.md 矛盾——官方只要求 Docker + Docker Compose，Helm 是 k8s 用户的可选项；实测 idle 仅约 100MB。
  • 媒体文章里的 Stars 数（10.7k / 23.7k / 40k）全部过时，真实值 48,124。

结论：Multica 相关的一切技术细节，只认 README.md / SELF_HOSTING.md / LICENSE 三个官方文件，其余当参考。

9. 结论与建议

如果目标是"搭一人公司"：Multica 不是最优解，建议先看 Paperclip。
Multica 的抽象是"派活"，Paperclip 的抽象是"建组织"。你要的是后者。

如果目标是"把我现有的多个 Agent CLI 管起来"：Multica 值得试，且 CodeBuddy 已在官方支持列表里。

三档建议

① 只取经，不落地 成本零，收益确定。重点读三份官方文件（README / VISION / SELF_HOSTING），把 Runtime 抽象、Autopilots、Review gates 三个设计思路吸收进 OPC 机制层。协议零风险，架构可借鉴。
② 接一个真场景试水 成本半天，收益可验证。用 Multica Cloud（不自建，避开 Docker + PG 运维 + 登录坑），把 CodeBuddy 接进去，跑一个真实工单。重点验证两个宣传点是否兑现："Agent 主动报 blocker" 和 "Skills 沉淀"。同时对照看 Paperclip 的 onboard（5 分钟，内嵌数据库）。
③ 作为 OPC 底座 不建议，至少现在不建议。三个理由：一是 OPC 的文件系统优势会被引进数据库依赖抵消；二是协议第①条挡住未来产品化；三是 v0.4.x 的编排能力还不闭环（子 Agent 丢失认证上下文这个坑没填）。真要上，等它把 #1943 Workflow Orchestration 和 agent API 访问这两个缺口补上再说。
最值得 OPC 借鉴的一点

Multica 那句 "It does not ship a model. It drives the agent CLIs you already have" —— 不做执行者，只做协调者。这个定位和 OPC 现在的角色高度一致：OPC 不生产 Agent 能力，它提供命名空间、稳定锚、门禁，让上层 Agent 能稳定协作。这个方向是对的，不必因为 Multica 火就动摇。
